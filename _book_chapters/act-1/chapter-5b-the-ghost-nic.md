Act I: Foundations of Breach

**Chapter 5b: Networking in the Shadows**

> **See also**: [Blog post]({{ site.baseurl }}/the-ghost-nic.html) · [POC code](https://github.com/mbhatt1/dBPF/tree/master/dBPF-pocs/pocs/ch05b-ghost-nic) · [Harness entry](https://github.com/mbhatt1/dBPF/blob/master/dBPF-pocs/harness/proof.py)

The primitive this chapter documents is a covert receiver attached to a network interface. UDP packets destined for port 31337 whose payload begins with the ASCII bytes `GHOST` are parsed by an XDP program, the trailing command bytes are copied into a ringbuf, and the packet is returned as `XDP_DROP` before any part of the kernel's IP stack or any userspace packet tap observes the frame. The POC lives in `dBPF-pocs/pocs/ch05b-ghost-nic/`. It consists of one BPF object (`ch05b-ghost-nic.bpf.c`, 69 lines), one userspace loader (`ch05b-ghost-nic.c`, 227 lines), one trigger script (`trigger.sh`, 177 lines), and a skeleton header generated by `bpftool gen skeleton`. The total compiled BPF program fits in a few hundred bytes of JIT output.

This chapter is a close reading of that code and of the architectural position it occupies. Every technical claim is cross-referenced against the source file and line it originates from. The goal is that a reader with a kernel source tree open on a second monitor can follow every assertion back to the exact mechanism in the kernel that makes it true.

## Why XDP, not tc

The first decision the POC made was where in the receive path to attach. The Linux kernel gives a BPF program several plausible hook points on ingress: a classifier attached to `tc` ingress via `cls_bpf`, an XDP program attached to the netdev, a socket filter attached to a specific raw socket, or an LSM hook on `socket_recvmsg`. Each of these sees the packet at a different layer and with different visibility to other observers. The goal here was to make the packet disappear not only from the IP stack but from every userspace tap that relies on the IP stack or on AF_PACKET. That narrowed the choice to one.

The layering is the load-bearing fact. A frame arriving at a network interface travels through a specific sequence of kernel hooks: the driver's `napi_gro_receive` accumulates the frame, `netif_receive_skb` dispatches it, and the dispatch walks a pipeline that includes, in order, the XDP program (if one is attached in native or generic mode), the `ptype_all` list (which is where `AF_PACKET` taps live), the `tc` ingress `cls_bpf` chain, and finally the protocol handler (`ip_rcv` for IPv4). Any hook earlier in the pipeline runs before any hook later in the pipeline. A program that returns `XDP_DROP` at the first step prevents every subsequent step from seeing the frame.

`tcpdump` is the common reference point because it is the tool a defender reaches for first. On Linux `tcpdump` opens an `AF_PACKET` socket and attaches it, via `packet_create` and `dev_add_pack`, to the `ptype_all` list. The kernel walks `ptype_all` in `__netif_receive_skb_core` after XDP has already run. A frame that XDP drops never reaches `ptype_all`, so no `AF_PACKET` socket sees it, so `tcpdump` records nothing. This is not a `tcpdump` bug; it is the documented layering of the receive path. The XDP hook predates the tap, by design.

`tc` ingress with a `cls_bpf` filter was the first alternative considered during POC development. A `cls_bpf` program can drop a frame (by returning `TC_ACT_SHOT`) just as cleanly as XDP can. The difference is temporal: the `cls_bpf` hook runs after the `ptype_all` walk, not before. A `tcpdump` running on the interface still captures the frame, because the tap fires before the tc ingress chain. That defeats the intent of the primitive, which is invisibility to existing observability. `tc` ingress was investigated and rejected for exactly this reason.

The socket filter option was rejected for a different reason. A socket filter attached to a raw socket via `setsockopt(SO_ATTACH_BPF)` sees only the frames that match the socket's existing filter, and dropping inside the filter only prevents that one socket from receiving the frame. Other sockets, other taps, and the normal IP stack all still see it. The filter is socket-local; the XDP program is interface-global.

The LSM hook was considered and rejected because there is no LSM hook on the RX path prior to the IP stack. `security_socket_recvmsg` runs when userspace calls `recvmsg` on a socket that has already dequeued a frame. By the time it fires, the frame has already passed through every earlier observer.

XDP was the only hook that ran early enough to prevent every other observer from seeing the frame. That is the architectural reason the POC uses XDP. The choice is not about performance, although XDP is the faster path; it is about position in the receive pipeline.

The position also matters for what the XDP program can do. An XDP program runs before the kernel has allocated an `sk_buff`. The program sees a raw packet buffer — `struct xdp_md` with `data` and `data_end` pointers into the driver's DMA region — and has five valid verdicts: `XDP_ABORTED` (error/drop with trace), `XDP_DROP` (discard the frame silently), `XDP_PASS` (hand the frame to the stack), `XDP_TX` (send it back out the same interface), and `XDP_REDIRECT` (redirect to a different interface or a CPU map). `XDP_DROP` is the verdict this POC uses, and it is implemented as a simple skip of the rest of the receive pipeline; no `sk_buff` is ever allocated, no protocol handler runs, no socket is notified.

The cost of this choice is that the XDP program does not have the kernel's IP/UDP parser available. It has only the raw bytes. The program must parse the Ethernet header, the IP header, and the UDP header by hand, and it must convince the verifier that every memory access is bounded. The bulk of the BPF source file is exactly this bounds-checking work. What the program gains in return is that its verdict precedes every other observer.

One further architectural point deserves emphasis. The XDP hook and the AF_PACKET tap are not at the same layer, but they also are not at adjacent layers — there is a specific call sequence that places AF_PACKET strictly downstream of XDP. In `net/core/dev.c`, the function `__netif_receive_skb_core` walks through the receive pipeline in order: first the generic XDP hook (in skb-mode), then the `dev_stat_inc(NET_RX_DROPPED)` counter updates for an `XDP_DROP` return, then the `ptype_all` walk that dispatches to AF_PACKET listeners, then the `ptype_base` walk that dispatches to protocol handlers, then the tc ingress chain. The XDP-drop short-circuit is a `goto drop` that skips every subsequent step. This is source-visible structure, not a quirk: the pipeline order is the kernel's supported contract. A defender's detection strategy that depends on AF_PACKET visibility is defeated by this ordering, not by any covert trick. The XDP program uses a publicly documented hook at a publicly documented position.

A related subtlety is that native XDP (drv-mode) and generic XDP (skb-mode) are at different positions, but both precede AF_PACKET. Native XDP runs in the driver's receive handler before `netif_receive_skb` is called; generic XDP runs inside `netif_receive_skb` at the top, before the `ptype_all` walk. The difference affects performance (native XDP avoids the `sk_buff` allocation entirely; generic XDP runs after the allocation but before any other use of the `sk_buff`) but does not affect the invisibility property. Both modes are upstream of AF_PACKET, and both produce `XDP_DROP` semantics that defeat `tcpdump`. This matters because `veth` is generic-only on many kernels, and the POC needs the invisibility property on `veth`.

## Source walk: progressive bounds checks

The BPF source file `ch05b-ghost-nic.bpf.c` is 69 lines of C. The core function is `xdp_ghost`, which is attached via `SEC("xdp")`. The function signature is the standard XDP signature:

```c
SEC("xdp")
int xdp_ghost(struct xdp_md *ctx)
{
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
```

`struct xdp_md` is the BPF-visible view of the XDP context. It has six fields exposed to BPF: `data`, `data_end`, `data_meta`, `ingress_ifindex`, `rx_queue_index`, and `egress_ifindex`. The `data` and `data_end` fields are 32-bit unsigned integers on the C side, but the verifier tracks them as packet pointers. The cast through `long` is a convention for converting these to usable `void *` pointers in the program's local scope. The verifier understands the cast and assigns the pointers its packet-pointer type, which is what enables the bounds-check machinery downstream.

The Ethernet header bounds check is the first work the function does:

```c
struct ethhdr *eth = data;
if ((void *)(eth + 1) > data_end) return XDP_PASS;
if (eth->h_proto != bpf_htons(0x0800)) return XDP_PASS;  // IPv4 only
```

`eth + 1` is pointer arithmetic on `struct ethhdr *`, so the expression evaluates to `data + sizeof(struct ethhdr)`. On all Linux architectures `sizeof(struct ethhdr)` is 14 bytes (6 bytes destination, 6 bytes source, 2 bytes ethertype). The check `(void *)(eth + 1) > data_end` asks whether the 14 bytes needed for the Ethernet header lie entirely within the packet buffer. If they do not, the program returns `XDP_PASS` and the kernel handles the (presumably malformed) frame through its normal path.

The verifier insists on this check. A program that reads `eth->h_proto` without first proving that `eth + 1 <= data_end` fails to load. The specific error the verifier produces is "invalid access to packet" with a byte offset — typically something like "R1 offset is outside of the packet". The check satisfies the verifier's proof obligation that every dereference of a packet pointer is within bounds. Skipping it is not an optimization; it is a load-time failure.

The ethertype filter is a defense against non-IPv4 traffic. `bpf_htons(0x0800)` is the ethertype for IPv4 in network byte order. The program returns `XDP_PASS` for any non-IPv4 frame, which means IPv6, ARP, VLAN-tagged, and encapsulated frames fall through to the normal stack. The POC is IPv4-only on purpose; extending to IPv6 requires parsing `struct ipv6hdr` (40 bytes, plus optional extension headers) and is left as a straightforward extension.

The IP header bounds check is the next layer:

```c
struct iphdr *ip = (void *)(eth + 1);
if ((void *)(ip + 1) > data_end) return XDP_PASS;
if (ip->protocol != 17) return XDP_PASS;  // UDP
```

The `ip` pointer is computed as the byte immediately after the Ethernet header. `sizeof(struct iphdr)` is 20 bytes (the minimum IPv4 header, with no options). The check `(void *)(ip + 1) > data_end` verifies that 20 more bytes lie within the packet buffer. If the frame is shorter than `eth + 20`, the program returns `XDP_PASS` and the kernel handles the malformed packet.

The protocol filter pulls `ip->protocol` out of the now-validated IP header. `17` is `IPPROTO_UDP`. Non-UDP traffic (TCP, ICMP, OSPF, etc.) falls through. If a defender captures with `tcpdump -i veth_g0 not udp` they see every non-UDP frame normally; the XDP program does not touch those.

The IP header length check handles the fact that IPv4 allows variable-length options:

```c
unsigned int ihl = ip->ihl * 4;
if (ihl < sizeof(*ip)) return XDP_PASS;
struct udphdr *udp = (void *)ip + ihl;
if ((void *)(udp + 1) > data_end) return XDP_PASS;
```

The `ihl` field is a 4-bit nibble in the first byte of the IP header encoding the header length in 32-bit words. A valid IPv4 header has `ihl >= 5` (20 bytes minimum); the maximum is `ihl == 15` (60 bytes). `ip->ihl * 4` converts the word count to a byte count. The `ihl < sizeof(*ip)` check (which is `ihl < 20`) rejects IP headers shorter than the minimum. In practice this catches the edge case where `ihl == 0` through `ihl == 4`, which is malformed, but the verifier wants a bounded value before it will let the program use `ihl` in pointer arithmetic.

The UDP header is then placed at `(void *)ip + ihl`, which is the byte after the IP header including any options. The bounds check `(void *)(udp + 1) > data_end` verifies that 8 more bytes (the UDP header) lie within the packet buffer. `sizeof(struct udphdr)` is 8 bytes: 2 bytes source port, 2 bytes destination port, 2 bytes length, 2 bytes checksum.

The destination port filter is the next gate:

```c
if (udp->dest != bpf_htons(GHOST_PORT)) return XDP_PASS;
```

`GHOST_PORT` is defined at the top of the file as `31337`. The port is a network-byte-order 16-bit value; `bpf_htons(31337)` converts the constant. Non-matching packets fall through. This single line reduces the program's matched traffic to a tiny fraction of the total — only UDP packets specifically destined for port 31337 survive the filter.

The magic-string check is the final gate before the program commits to processing the packet:

```c
char *payload = (char *)(udp + 1);
if (payload + 5 > (char *)data_end) return XDP_PASS;
if (!(payload[0]=='G' && payload[1]=='H' && payload[2]=='O' &&
      payload[3]=='S' && payload[4]=='T')) return XDP_PASS;
```

The payload starts immediately after the UDP header. The bounds check `payload + 5 > (char *)data_end` verifies that at least 5 bytes of payload exist. The comparison is a byte-by-byte check against the literal ASCII string `GHOST`. A packet that reaches this point but does not begin with these five bytes falls through, which means UDP/31337 packets with arbitrary payloads from legitimate traffic are not disturbed. Only the packets that match the magic prefix are swallowed.

The cumulative effect of the five bounds checks plus the ethertype, protocol, port, and magic filters is that the program examines every ingress frame but commits to the covert-channel fast path only when all filters pass. The typical packet (a TCP flow, a stray ARP, an IPv6 neighbor solicitation) traverses three or four lines of C and returns `XDP_PASS` with a few dozen nanoseconds of overhead. Only packets that match the entire filter chain reach the ringbuf-emit code.

Each of the bounds checks is verifier-mandated. Removing any one of them produces a specific load-time error. Removing the Ethernet bounds check gives "invalid access to packet" on the `eth->h_proto` read. Removing the IP bounds check gives the same error on the `ip->protocol` read. Removing the `ihl` minimum check gives "unbounded memory access" on the `(void *)ip + ihl` computation, because the verifier cannot prove the resulting pointer is in bounds without a lower bound on `ihl`. Removing the UDP bounds check gives "invalid access to packet" on the `udp->dest` read. Removing the payload length check gives "invalid access to packet" on the `payload[0]` read. The checks are not style; they are a proof that the verifier requires.

The order of the checks is also load-bearing. The verifier's proof tracking is linear through the program. A check that happens after a dereference cannot satisfy the verifier's obligation for that dereference. The program must prove bounds before it uses them, in source order. Reordering the checks to put them all at the top in one block and then doing all the reads in a second block is a common style but the verifier accepts the interleaved form used here with equal enthusiasm. The key is that each individual read is preceded, in control-flow order, by a check that proves it is in bounds.

The `bpf_htons(0x0800)` constant deserves a brief aside because it is a common source of confusion. The ethertype field in the Ethernet header is stored in network byte order, which is big-endian. The constant `0x0800` is the host-byte-order representation of IPv4's ethertype. `bpf_htons` converts the constant to network byte order at compile time — the verifier sees it as a plain constant, not a helper call. On a big-endian host, `bpf_htons(0x0800)` is the identity; on a little-endian host, it is a byte swap. The macro expands to `__builtin_bswap16(0x0800)` on little-endian and to `0x0800` on big-endian, with the compiler constant-folding the result. Comparing `eth->h_proto` directly against `0x0800` without the macro works on big-endian hosts (aarch64 big-endian, SPARC) and fails on little-endian hosts (x86_64, aarch64 little-endian, which is the common case). The BPF convention is to always convert with `bpf_htons` or `bpf_ntohs`; the conversion is free.

The `ip->ihl * 4` computation is the one arithmetic operation in the header parse and deserves its own verifier note. The field `ihl` is a 4-bit unsigned quantity (0–15). The multiplication by 4 gives a value in [0, 60], which the verifier tracks as a bounded integer. The subsequent `(void *)ip + ihl` pointer arithmetic is acceptable to the verifier because the bound on `ihl` is known. If the program tried to use `ip->tot_len` (a 16-bit field with range [0, 65535]) in pointer arithmetic without masking, the verifier would reject the program because the bound is too loose for the packet pointer's available range. This is the general shape of verifier-acceptable pointer arithmetic: the offset must have a small, provably bounded range, and the resulting pointer must be demonstrably within `[data, data_end]`.

A verifier error message worth recognizing for this POC is "math between pkt pointer and register with unbounded min value is not allowed." This surfaces when a pointer is offset by a value whose lower bound the verifier cannot prove is non-negative. The POC avoids this by using unsigned integer types throughout and by the implicit lower bound of zero on `ihl * 4`. A sloppier version that used signed arithmetic, or that computed offsets from untrusted network data without clamping, would produce this error.

The unrolled-loop pragma on the command-copy loop deserves revisiting here because it is tied to the verifier's acceptance of the bounds check inside the loop body. Without `#pragma unroll`, the compiler emits a loop with a trip count that depends on the first NUL in the source data. The verifier would need to prove at each iteration that `cmd_src + i + 1 <= data_end`, and because `i` is loop-dependent, the proof obligation compounds. Modern verifiers (5.3+) support bounded loops and can handle this, but the unrolled form is unambiguously correct at every BPF bytecode offset, which avoids any reliance on the bounded-loop feature. For a POC that aims to load on 5.x through 6.x without modification, the unrolled form is the portable choice.

## The command exfil

Once all the filters have passed, the program has identified a packet that warrants handling. The next work is to copy the command bytes out of the packet and into the ringbuf:

```c
struct evt *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
if (!e) return XDP_DROP;
e->saddr = ip->saddr;
e->daddr = ip->daddr;
e->sport = bpf_ntohs(udp->source);
e->dport = bpf_ntohs(udp->dest);
__builtin_memset(&e->cmd, 0, sizeof(e->cmd));
```

The `struct evt` layout is declared at the top of the source file:

```c
struct evt {
    unsigned int saddr;
    unsigned int daddr;
    unsigned short sport;
    unsigned short dport;
    char cmd[48];
};
```

Four network-identifying fields plus a 48-byte command buffer. The total size is 60 bytes before alignment; on aarch64 with the struct's natural alignment, it rounds to 64 bytes. The ringbuf reservation is for `sizeof(*e)` bytes. If the ringbuf is full, `bpf_ringbuf_reserve` returns `NULL` and the program returns `XDP_DROP` anyway — the packet disappears from the stack even if the event cannot be delivered to userspace. This is a deliberate design choice: the primitive's first job is to drop the packet; event delivery is a secondary goal.

The `bpf_ntohs` calls on the ports convert from network byte order to host byte order for userspace consumption. The `saddr` and `daddr` fields are written in network byte order and converted by the userspace consumer using `inet_ntop`, which expects network byte order. The `__builtin_memset` zeros the command buffer before the byte-copy loop, so unused bytes are always `0` rather than random stack junk.

The byte-copy loop is the core of the exfil:

```c
char *cmd_src = payload + 5;
unsigned int i = 0;
#pragma unroll
for (i = 0; i < sizeof(e->cmd) - 1; i++) {
    if (cmd_src + i + 1 > (char *)data_end) break;
    e->cmd[i] = cmd_src[i];
    if (cmd_src[i] == 0) break;
}
bpf_ringbuf_submit(e, 0);
return XDP_DROP;
```

`cmd_src` points to the byte immediately after the 5-byte `GHOST` magic. `sizeof(e->cmd) - 1` is 47, which is the number of command bytes the program will copy (reserving one byte for the trailing NUL, which is already zeroed by the memset). The loop has three exit conditions: reaching the 47-byte cap, running out of packet bytes, or hitting a NUL in the source.

The `#pragma unroll` directive instructs the compiler to unroll the loop at compile time. This is important for the verifier. A loop with a variable trip count is something the verifier can handle with bounded-loop support on 5.3+, but an unrolled loop is unambiguously bounded at compile time and always loads cleanly. The unroll produces 47 copies of the three-line loop body, which compiles to a few hundred bytes of BPF bytecode. This is still well under the per-program instruction limit (1 million on modern kernels).

The bounds check `cmd_src + i + 1 > (char *)data_end` is inside the loop body because the verifier tracks packet-pointer bounds at each iteration. Without this check, the `cmd_src[i]` read would fail verification at the first iteration that could plausibly walk off the end of the packet. With the check, the verifier sees an explicit bound on the read at each offset.

The 47-byte cap on command length is a fundamental limitation of the primitive. A command longer than 47 bytes is either truncated (if the source has more) or terminated early (if the source has a NUL). The cap is chosen to keep the event struct at a friendly 64-byte alignment after the ringbuf's 8-byte alignment tax; it can be raised, at the cost of larger per-event memory, by growing the struct.

`bpf_ringbuf_submit` commits the reservation and makes the event visible to the userspace consumer. The helper is a no-op on the packet; it just updates the ringbuf's producer index. The program then returns `XDP_DROP`, and the kernel discards the frame.

The combination of these steps — reserve, fill, submit, drop — is atomic from the perspective of the userspace consumer. Either the event is visible in the ringbuf and the packet was dropped, or the event is missing and the packet was still dropped (if the ringbuf was full). There is no intermediate state in which the packet survives because the event could not be reserved.

## XDP_DROP, explained

The semantic of `XDP_DROP` deserves its own section because the absence of downstream behavior is the feature. When the driver's XDP dispatch receives `XDP_DROP` from the attached program, it takes a specific sequence of actions, and everything it does not do is important.

What the driver does: it decrements an `rx_dropped` counter, which is visible via `ip -s link show <if>` as the `dropped` field, and it releases the packet buffer back to the receive pool. What the driver does not do: it does not allocate an `sk_buff`, it does not call `netif_receive_skb`, it does not walk the `ptype_all` list, it does not invoke tc ingress, it does not call any protocol handler, it does not signal any socket, and it does not emit any netfilter hook.

The consequences propagate outward. `tcpdump` on the interface sees nothing because `tcpdump` depends on `AF_PACKET`, which depends on `ptype_all`, which is never walked. `nftables` and `iptables` see nothing because they are implemented as netfilter hooks, and the netfilter hooks are invoked from protocol handlers (`ip_rcv`, `tcp_v4_rcv`, `udp_rcv`), none of which run. Raw sockets see nothing because the kernel never calls `__skb_try_recv_datagram`. Connection tracking sees nothing because `nf_conntrack_in` is a netfilter hook invoked during protocol processing. A listening UDP socket bound to port 31337 sees nothing because `udp_rcv` is never called for this packet.

The sender's TCP/UDP stack sees nothing either. `XDP_DROP` is a silent drop. There is no ICMP Destination Unreachable (that would require the IP stack to run), there is no TCP RST (that would require `tcp_v4_rcv` to run and decide to reject), there is no closure signal back to the sender. From the sender's perspective, a `GHOST` packet is indistinguishable from a packet that was lost in transit. The sender receives no feedback.

This is exactly the behavior the covert channel wants. A legitimate UDP sender retries, times out, or gives up depending on its application-level protocol; the covert-channel sender uses one-shot fire-and-forget semantics and does not rely on any feedback from the receiver. The silence of `XDP_DROP` is what makes the channel hard to notice from the sender side too. A defender inspecting network flows from an egress point sees the UDP packet leaving the sender; it cannot tell, from the egress side alone, whether the packet was received-and-dropped or received-and-processed.

The flip side of this invisibility is that the driver's counters do still tick. `ip -s link show veth_g0` reports the `dropped` counter incrementing, and a defender who baselines the counters and looks for anomalous drops can detect the primitive at that level. This is discussed in the detection section below.

## Loader attach modes

The userspace loader `ch05b-ghost-nic.c` is responsible for loading the BPF object, attaching the XDP program to an interface, and consuming the ringbuf. The attach step is the interesting one because XDP has three attach modes with different capability requirements.

The mode choice is made in the loader around line 167:

```c
int err = -1;
if (!skb_only) {
    err = bpf_xdp_attach(ifindex, prog_fd, XDP_FLAGS_DRV_MODE, NULL);
    if (err) {
        fprintf(stderr, "[ghost] drv-mode attach failed (%s), falling back to skb-mode\n",
                strerror(-err));
    } else {
        g_xdp_flags = XDP_FLAGS_DRV_MODE;
        attached = 1;
        fprintf(stderr, "[ghost] attached XDP (drv-mode) to %s ifindex=%d\n", ifname, ifindex);
    }
}
if (!attached) {
    err = bpf_xdp_attach(ifindex, prog_fd, XDP_FLAGS_SKB_MODE, NULL);
    ...
}
```

Two modes are attempted in order. `XDP_FLAGS_DRV_MODE` is native XDP, which runs the program in the driver's receive path before the `sk_buff` is allocated. `XDP_FLAGS_SKB_MODE` is generic XDP, which runs the program in `netif_receive_skb` after the `sk_buff` has been allocated. The third mode, not used here, is `XDP_FLAGS_HW_MODE`, which offloads the program to a smart NIC.

Native XDP has lower overhead because it runs on the driver's raw DMA buffer and avoids the `sk_buff` allocation. Generic XDP has higher overhead (measured in tens of nanoseconds per packet on commodity hardware) but runs on any interface the kernel knows about, including software-only interfaces that have no driver in the traditional sense. The tradeoff is that native XDP requires driver support; generic XDP does not.

`veth` (virtual Ethernet pair) is a software-only interface. The driver for `veth` is in `drivers/net/veth.c`. It does have native XDP support on kernels 4.19 and newer, but the support is conditional and depends on the peer interface also having XDP attached. On the linuxkit 6.12 aarch64 kernel used for the harness, native XDP on veth is flaky; generic XDP is the reliable choice. The loader's fallback logic handles this: it tries drv-mode first and silently falls back to skb-mode if drv-mode rejects the attach.

The trigger script explicitly forces skb-mode by passing `-S`:

```bash
"$LOADER" -S -i veth_g0 >"$LOG_LOADER" 2>&1 &
```

This avoids the fallback and makes the harness deterministic across kernels. On a production-grade NIC driver (mlx5, i40e, ixgbe), the drv-mode path works without fallback and the program runs with the full XDP performance profile.

The `bpf_xdp_attach` helper is a libbpf wrapper around the `BPF_LINK_CREATE` command of the `bpf(2)` syscall with `BPF_LINK_TYPE_XDP`. The syscall creates a link object that holds the program attached to the netdev. The link is owned by the process; when the process exits without calling `bpf_xdp_detach`, the link remains and the program stays attached until something explicitly removes it or the netdev is deleted.

The loader's cleanup path at line 213 handles detach on every exit path:

```c
if (attached) {
    int derr = bpf_xdp_detach(g_ifindex, g_xdp_flags, NULL);
    if (derr)
        fprintf(stderr, "[ghost] bpf_xdp_detach: %s\n", strerror(-derr));
    else
        fprintf(stderr, "[ghost] detached XDP from ifindex=%d\n", g_ifindex);
}
```

This runs on success, on error, on signal interrupt, and on any other exit path. Without it, a loader that is killed with `SIGKILL` or that segfaults leaves the XDP attachment dangling on the netdev until the netdev itself is deleted or the attachment is manually cleared with `ip link set dev <if> xdp off`. The dangling attachment is a detection signature of its own — a defender who sees an XDP program attached without a corresponding running loader has found the residue of a terminated covert receiver.

The mode the loader ends up in is reported by `bpftool net show`. For skb-mode, the output shows `generic`:

```
xdp:
veth_g0(13) generic id 52
```

For drv-mode, the output shows the interface's driver identifier. The `id 52` is the BPF program ID that `bpftool prog show` can cross-reference. A defender who dumps `bpftool net show` periodically catches every XDP attachment system-wide.

The loader's signal-handling strategy deserves a brief note because it is what makes the detach cleanup reliable. The handler is installed early, before `open_and_load`:

```c
struct sigaction sa = { .sa_handler = on_signal };
sigemptyset(&sa.sa_mask);
sa.sa_flags = 0;
if (sigaction(SIGINT, &sa, NULL) < 0 || sigaction(SIGTERM, &sa, NULL) < 0) { ... }
```

`sa.sa_flags = 0` explicitly clears `SA_RESTART`. The consequence is that system calls interrupted by a signal do not automatically restart; instead, they return `-1` with `errno == EINTR`. For `ring_buffer__poll`, this manifests as a `-EINTR` return, which the main loop explicitly handles:

```c
while (!stop) {
    int n = ring_buffer__poll(rb, 200);
    if (n < 0) {
        if (n == -EINTR)
            break; /* signal during poll → fall through to cleanup */
        fprintf(stderr, "[ghost] ring_buffer__poll: %s\n", strerror(-n));
        break;
    }
}
```

Without the `SA_RESTART`-clear plus the explicit `-EINTR` check, a SIGINT during poll would loop indefinitely until the next ring-buffer event arrived (which for a ringbuf with no traffic would be the 200ms timeout, so not infinitely — but noticeably laggy). The explicit handling makes Ctrl-C responsive.

The cleanup path uses `goto out` from every error location, with `attached`, `rb`, and `skel` guarding the conditional cleanups:

```c
out:
    if (attached) {
        int derr = bpf_xdp_detach(g_ifindex, g_xdp_flags, NULL);
        ...
    }
    if (rb)
        ring_buffer__free(rb);
    if (skel)
        ch05b_ghost_nic_bpf__destroy(skel);
    fprintf(stderr, "[ghost] shutdown (rc=%d)\n", rc);
    return rc;
```

This pattern — a single cleanup label reached by `goto` from every error, with each resource guarded by a boolean flag set when it was acquired — is the C idiom for RAII-like cleanup. The alternative (nested `if` blocks with cleanup in each) is harder to verify correct and more prone to missed cleanups when a new error path is added. The goto-to-cleanup idiom is what the Linux kernel itself uses for error handling in most functions. The loader follows the convention.

`g_ifindex` and `g_xdp_flags` are file-scope statics rather than stack locals because the signal handler comments mention they might, in a future revision, be read by an async-signal-safe detach path. In the current revision the handler just flips the `stop` flag, but the file-scope declaration leaves the option open without requiring a future refactor. This is a small forward-compatibility choice worth noting because it is the kind of thing that would be easy to break in an edit.

## Harness behavior

The harness entry for this POC lives in `dBPF-pocs/harness/proof.py` at line 83:

```python
Poc("ch05b", "Ghost NIC (XDP UDP:31337)", "ch05b-ghost-nic",
    hooks=["veth"], prefix="[ghost]", mode="trigger-runs-loader",
    timeout=20,
    proof_marker=r"GHOST_COVERT_CHANNEL_PROVEN"),
```

The entry uses `mode="trigger-runs-loader"`, which means the trigger script is responsible for running the loader itself. This is different from the default mode where the harness runs the loader and the trigger drives it; for POCs that need veth/netns setup, the trigger owns the full lifecycle. The `hooks=["veth"]` field documents that the attach target is a veth interface, which is informational rather than load-bearing (the harness does not use it to precheck). The `timeout=20` caps the POC at 20 seconds; real execution is 2–3 seconds.

The proof marker is `GHOST_COVERT_CHANNEL_PROVEN`. The trigger emits this marker with two fields:

```bash
echo "=== GHOST_COVERT_CHANNEL_PROVEN dropped=${RINGBUF_COUNT} tcpdump=${AFTER_COUNT} ==="
```

`RINGBUF_COUNT` is the number of `[ghost] DROPPED` lines in the loader log, which is the number of events the BPF program emitted to the ringbuf. `AFTER_COUNT` is the number of UDP/31337 frames `tcpdump` captured during the AFTER phase, when XDP was active. The harness considers the POC proven when `RINGBUF_COUNT > 0` and `AFTER_COUNT == 0` — commands delivered via the covert channel, zero frames visible to the packet tap.

The trigger script creates its own veth pair and network namespace in the setup block:

```bash
ip netns add ghost_ns 2>/dev/null
ip link add veth_g0 type veth peer name veth_g1 || { echo "veth add failed"; exit 1; }
ip link set veth_g1 netns ghost_ns
ip addr add 10.66.66.1/24 dev veth_g0
ip -n ghost_ns addr add 10.66.66.2/24 dev veth_g1
ip link set veth_g0 up
ip -n ghost_ns link set veth_g1 up
```

`veth_g0` lives in the host namespace; `veth_g1` lives in the `ghost_ns` namespace. The XDP program attaches to `veth_g0` on the host side. An attacker process running inside `ghost_ns` sends UDP to `10.66.66.1:31337`, which arrives on `veth_g0` and is intercepted by the XDP program before it can traverse the host's IP stack.

The packet send is a three-line Python snippet in the trigger:

```bash
ip netns exec ghost_ns python3 -c '
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.sendto(b"GHOST/bin/id > /tmp/pwned", ("10.66.66.1", 31337))
s.sendto(b"GHOSTexfil-command-2", ("10.66.66.1", 31337))
```

Two UDP packets, one with a 23-byte command, one with a 15-byte command. The trigger runs `tcpdump -i veth_g0 -c 2 udp port 31337` in parallel to record how many the packet tap sees. Before XDP is attached, the tap sees both; after XDP is attached, the tap sees zero and the loader's ringbuf gets two `[ghost] DROPPED` lines. The before/after comparison is what makes the invisibility claim falsifiable.

## Cross-kernel

XDP has been stable since Linux 4.8 (October 2016). The `xdp_md` struct, the `XDP_PASS`/`XDP_DROP`/`XDP_TX`/`XDP_ABORTED` verdicts, and the basic attach path have not changed in meaningful ways. Programs written against the 4.8 XDP ABI load on 6.12 without modification.

What has changed is the verifier's strictness. On 4.x kernels, a program that did the bounds checks in a different order or with coarser granularity was more likely to be accepted. The 5.x verifier tightened the packet-pointer tracking and rejects programs that would have loaded on 4.x — specifically, programs that rely on implicit bounds propagation through variable-length headers. The POC's explicit `ihl < sizeof(*ip)` check is an example of a check that is needed on 5.x+ but was sometimes optional on 4.x.

`XDP_REDIRECT` was added in 4.14 and is the basis for later work — `bpf_redirect_map`, `cpumap`, and the `AF_XDP` sockets that ship packets to userspace with zero copies. The ch05b POC does not use redirect; it uses drop. Redirect is what Chapter 15 of this book builds on.

The `bpf_xdp_attach` and `bpf_xdp_detach` libbpf functions were introduced in libbpf 0.7 as wrappers around the older `bpf_set_link_xdp_fd` helper. The older function is still present and works identically. The newer `BPF_LINK_CREATE`-based attach (used internally by `bpf_xdp_attach`) is preferred on 5.7+ kernels because the resulting link object supports the `BPF_F_REPLACE` flag for atomic program swaps.

Ringbuf (`BPF_MAP_TYPE_RINGBUF`) was introduced in 5.8. On earlier kernels, a similar pattern uses perf event arrays (`BPF_MAP_TYPE_PERF_EVENT_ARRAY`) with `bpf_perf_event_output`. The perf-event-array path is more complicated to set up and has higher per-event overhead; ringbuf is the current-best option and is used here.

The veth driver's XDP support was added in 4.19 (commit `948d4f214fde`, December 2018) for the transmit-side redirection case and expanded in 5.2 to cover the receive path more generally. Between 4.19 and 5.2, attaching an XDP program to veth in drv-mode succeeded only when the peer interface also had an XDP program attached; attaching to one side of a pair without the other was silently downgraded to a no-op. The symptom was that `XDP_DROP` returned from the program would not actually drop the frame — the frame would continue up the stack and `tcpdump` would see it. This behavior was fixed in 5.2, but kernels older than 5.2 still exhibit the bug in their drv-mode veth path. The skb-mode fallback avoids the bug by not relying on driver-specific code. For any kernel older than 5.2 or for any veth-based test setup where driver support is uncertain, forcing skb-mode via `-S` is the robust choice.

The `bpf_ntohs` helper in the event-emission path deserves a cross-kernel note. `bpf_ntohs` is actually a compile-time macro in `bpf_endian.h`, not a BPF helper function. It expands to `__builtin_bswap16` on little-endian hosts and to identity on big-endian hosts, the same as its userspace cousin. The verifier sees the result as a plain arithmetic operation on a value the BPF program already read from the packet. This is why it works without being on the helper allowlist — it is not a helper. The same is true of `bpf_htons`, `bpf_ntohl`, and `bpf_htonl`. The verifier's helper whitelist applies only to functions like `bpf_ringbuf_reserve`, `bpf_ringbuf_submit`, `bpf_get_current_pid_tgid`, and the handful of other entries in `kernel/bpf/helpers.c` and its siblings. Byte-order conversions are pure compiler intrinsics and require no runtime support.

## Detection

The XDP attachment is visible to any defender who looks. The primary detection layer is `ip link show`:

```
# ip link show veth_g0
13: veth_g0@veth_g1: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 xdpgeneric qdisc noqueue ...
    link/ether ae:... brd ff:ff:ff:ff:ff:ff
    prog/xdp id 52 tag a1b2c3d4 jited
```

The `xdpgeneric` flag in the flags list and the `prog/xdp id 52` annotation together identify an XDP program attached in skb-mode with program ID 52. For drv-mode the flag is `xdp`, for hw-mode it is `xdpoffload`. Any of these on an interface that should not have an XDP program is a strong signal.

The second detection layer is `bpftool net show`, which lists every XDP attachment system-wide:

```
# bpftool net show
xdp:
veth_g0(13) generic id 52

tc:
```

This is the single query that gives a defender a complete inventory of XDP programs. A baseline-diff approach, where a scheduled job captures `bpftool net show --json` hourly and compares against the previous snapshot, catches new XDP attachments within the scheduling interval. The output is small (a few hundred bytes on a typical host) and the diff is cheap.

The third detection layer is `bpftool prog show id <n>`, which gives the program's name, attach type, load time, and loader process context:

```
# bpftool prog show id 52
52: xdp  name xdp_ghost  tag a1b2c3d4 gpl
    loaded_at 2025-02-04T15:22:08+0000  uid 0
    xlated 520B  jited 680B  memlock 4096B  map_ids 14
```

The `name xdp_ghost` is the BPF program name from the SEC annotation. A defender maintaining an allowlist of known XDP program names catches attachments with unfamiliar names.

The fourth detection layer is netdev counter anomaly. An XDP program that drops packets increments the `rx_dropped` counter without corresponding errors in the TCP/UDP/ICMP stack:

```
# ip -s link show veth_g0
13: veth_g0@veth_g1: ...
    RX:  bytes  packets  errors  dropped  ...
              2100       30        0       30
```

A healthy interface has `dropped == 0` or close to it; a nonzero `dropped` paired with XDP attachment and no protocol-level errors is the signature of an XDP drop. A defender who baselines drop counters can detect the primitive even on kernels where direct XDP introspection is disabled (rare, but possible on hardened builds).

The fifth detection layer is BPF filesystem pinning. If the loader pins the XDP program at `/sys/fs/bpf/xdp_ghost`, the pin is visible via directory listing. The POC does not pin, but a production tool would.

The unexpected XDP attachment on a veth interface deserves special consideration. veth exists to provide network connectivity between namespaces, typically for containers. Legitimate use cases for XDP on veth are narrow: Cilium uses it for pod-to-pod load balancing on Kubernetes, and a few niche service meshes use it for similar purposes. An XDP attachment on a veth that is not part of a known networking stack is a high-signal anomaly.

## Scope

The primitive documented here is a Class IV primitive in the taxonomy developed in Chapter 20. A Class IV primitive removes a kernel subsystem's visibility from the defender's observability stack by occupying an architectural position below the defender's instrumentation. This is not a netfilter bypass in the sense of evading a specific rule; it is an architectural layer below netfilter by design.

The distinction matters for threat modeling. A netfilter bypass typically exploits a rule misconfiguration, a rule-order bug, or a protocol parsing error in a specific netfilter module. The fix is to tighten the rule. A Class IV primitive does not exploit a bug; it uses a supported kernel feature that runs in a position where the defender's instrumentation cannot reach. The fix is not to tighten a rule; it is to add instrumentation at the position the primitive occupies. XDP program introspection via `bpftool`, baseline diffing, and EDR-level XDP monitoring are the appropriate responses.

Existing observability that depends on netfilter, tcpdump, AF_PACKET, or any kernel ingress hook that runs after XDP is blind to this primitive by construction. This is not a gap in those tools; it is the design of the receive pipeline. The defender who wants to see what the ghost receiver sees must instrument at the XDP layer itself or at a layer that inspects BPF program attachments directly.

The primitive's offensive value is bounded by the detection signatures listed above. On any host with routine BPF program auditing, the primitive is visible. The attacker's advantage is not that the primitive is undetectable but that it is undetectable from within the network-layer observability stack alone. The defender who relies solely on tcpdump, iptables logs, and conntrack state has no view into XDP drops; the defender who also runs `bpftool net show` does.

## Prior art

The XDP subsystem has been used for legitimate purposes since its introduction. Cilium has used XDP since roughly 2018 for pod-to-pod load balancing and DDoS mitigation on Kubernetes clusters. The Cilium data plane attaches XDP programs to every pod's veth interface in exactly the way this POC does; the difference is that Cilium's programs return `XDP_REDIRECT` to a backend pod, not `XDP_DROP`. The attach mechanics are identical.

Suricata has XDP offload support for its IDS engine, which uses XDP on the receive path to filter traffic before it reaches the IDS's user-space analyzer. Facebook's Katran load balancer is an XDP-based load balancer for Facebook's front-end traffic. Cloudflare's L4Drop is a DDoS-mitigation XDP program that drops malicious traffic at the driver level. All of these use the same XDP APIs this POC uses.

The XDP tutorial project maintained by the XDP working group at `github.com/xdp-project/xdp-tutorial` is the canonical reference for XDP programming. It covers packet parsing, redirect, AF_XDP sockets, and a number of other XDP patterns. The POC's packet-parsing structure is the same shape the tutorial documents — progressive bounds checks followed by per-layer protocol filters.

The covert-channel aspect of the primitive (drop after identifying a magic prefix) does not appear in the legitimate XDP literature because legitimate uses do not want to hide packets from observers. The adaptation of existing XDP plumbing to a receive-but-do-not-deliver pattern is what distinguishes this primitive from the load-balancer/IDS/DDoS applications. The underlying mechanics — attach, parse, drop, emit-to-ringbuf — are the same.

The academic literature on kernel covert channels predates XDP by decades. The early work (Wray 1991, Kang et al. 1995) focuses on timing channels and storage channels in multilevel secure systems. More recent work (Percival 2005, Liu et al. 2015) examines cache-based side channels. The XDP-based receive channel is a newer primitive in this lineage; it is closest in shape to the "covert receiver" patterns that use raw sockets to see frames that would otherwise be filtered. The XDP variant improves on raw-socket receivers by also being invisible to other observers on the same host, which the raw-socket variant is not.

The research literature on XDP itself has grown steadily since 2018. Høiland-Jørgensen et al.'s "The eXpress Data Path" (CoNEXT 2018) is the canonical introduction, with performance measurements on commodity hardware showing single-digit-microsecond per-packet overhead for XDP programs of the kind this POC uses. Miano et al.'s "Creating Complex Network Services with eBPF" (ANRW 2019) covers multi-program XDP pipelines that compose drop, redirect, and pass verdicts. Vieira et al.'s "Fast Packet Processing with eBPF and XDP" (ACM Computing Surveys, 2020) is a survey of the design space. Readers interested in the performance and semantics of XDP in more depth than this chapter provides should start there.

The defensive-side literature on XDP detection is less mature. Most enterprise EDR products added BPF program inventory as a feature between 2021 and 2023. CrowdStrike's Falcon sensor added BPF visibility in a 2022 release; Microsoft Defender for Endpoint added it in the same timeframe. The detection strategies these tools implement are variants of the `bpftool`-based inventory described in the detection section above, scaled to an agent that runs continuously and reports deltas to a central collector. The academic-detection literature is sparse: there are a handful of research-prototype detectors (e.g., Jia et al., "Programmable In-Kernel Malware Detection with BPF," DSN 2023) but no established defensive stack that treats XDP attachment as a signal the way the commercial tools now do.

The interaction with container networking is worth a paragraph of its own. In the Kubernetes ecosystem, every pod has a veth pair: one end lives in the pod's network namespace, the other lives in the host's root namespace. Cilium installs XDP programs on the host-side veth for load balancing and policy enforcement. Calico in VPP mode does something similar. Other CNI plugins (the default bridge CNI, Flannel, Weave) do not use XDP. A defender operating on a Kubernetes node asks two questions: what CNI is installed, and does the CNI use XDP? If the CNI uses XDP, a baseline of expected XDP program names on each veth is the starting point. If the CNI does not use XDP, any XDP attachment on a veth is anomalous. For the POC's specific case — an XDP program attached to a veth on a host without Cilium/Calico/VPP — the attachment is anomalous by definition.

The adversary-simulation community has been slower to pick up XDP-based covert channels than the defender community has been to pick up XDP detection. The MITRE ATT&CK framework, as of the 2024 revision, does not have a specific sub-technique for XDP-based receivers; the closest entry is T1205 (Traffic Signaling), which covers magic-byte-triggered receivers generically. Extending T1205 with an XDP-specific sub-technique would be a useful contribution to the framework; the distinguishing property of the XDP variant is the invisibility to AF_PACKET/netfilter/tc-ingress observers that the generic traffic-signaling technique does not have. Until and unless the framework is extended, defenders following ATT&CK guidance as a baseline should know that T1205 as currently documented does not cover this variant.

```c
// The core match-and-drop, from ch05b-ghost-nic.bpf.c.
SEC("xdp")
int xdp_ghost(struct xdp_md *ctx)
{
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end) return XDP_PASS;
    if (eth->h_proto != bpf_htons(0x0800)) return XDP_PASS;

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end) return XDP_PASS;
    if (ip->protocol != 17) return XDP_PASS;

    unsigned int ihl = ip->ihl * 4;
    if (ihl < sizeof(*ip)) return XDP_PASS;
    struct udphdr *udp = (void *)ip + ihl;
    if ((void *)(udp + 1) > data_end) return XDP_PASS;
    if (udp->dest != bpf_htons(GHOST_PORT)) return XDP_PASS;

    char *payload = (char *)(udp + 1);
    if (payload + 5 > (char *)data_end) return XDP_PASS;
    if (!(payload[0]=='G' && payload[1]=='H' && payload[2]=='O' &&
          payload[3]=='S' && payload[4]=='T')) return XDP_PASS;

    // ... ringbuf submit and XDP_DROP follow ...
    return XDP_DROP;
}
```
