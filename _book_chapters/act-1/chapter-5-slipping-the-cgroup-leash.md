# Chapter 5: Slipping the Cgroup Leash

> **See also**: [Blog post]({{ site.baseurl }}/slipping-the-cgroup-leash.html) · [POC code](https://github.com/mbhatt1/dBPF/tree/master/dBPF-pocs/pocs/ch05-cgroup-leash) · [Harness entry](https://github.com/mbhatt1/dBPF/blob/master/dBPF-pocs/harness/proof.py)

> **Proof status**: `ch05-cgroup-leash` has been proved on Ubuntu 6.17.0 aarch64 (Lima VM, kernel 6.17.0-29-generic). No code changes were required.

The cgroup accounting path on Linux is two-sided. On one side, the scheduler tracks what each cgroup actually runs. That side is not the target of this chapter. On the other side, userspace reads `cpu.stat` to find out what the scheduler recorded. That readback is the target. The POC in `dBPF-pocs/pocs/ch05-cgroup-leash/` does not change what the kernel accounts; it changes what the kernel reports when userspace asks. The scheduler keeps throttling a cgroup that exceeds its quota. Every monitoring agent reading `/sys/fs/cgroup/cpu.stat` on that cgroup sees `usage_usec 0`.

## The readback path is the target

`cgroup_account_cputime` (an inline in `include/linux/cgroup.h`, called from `kernel/sched/fair.c`) updates the scheduler's internal counters. That function is not hooked. No BPF helper exists to `bpf_update_cgroup_cpu_stat(cgrp, fake)` the way earlier drafts of this chapter imagined. The kernel's scheduler is the source of truth for cgroup accounting, and it stays the source of truth throughout the attack.

What the POC does is shorter and more boring. It waits for a process to open `cpu.stat`, waits for the subsequent `read()` to complete, then overwrites the returned bytes in userspace memory with a constant string of zeros before the reader's `read()` returns. The kernel read path ran. The scheduler provided the real numbers. The kernel-side tracefs virtual file synthesized them into the ASCII output. Those bytes were copied to the user buffer. Between that copy and the reader regaining control, a BPF program running in the `sys_exit_read` tracepoint overwrote the user buffer.

The reader sees `usage_usec 0`. Everyone upstream of the reader — Prometheus, Grafana, Datadog, Netdata, cAdvisor, k8s metrics-server, Sysdig — sees `usage_usec 0`. The scheduler still throttles the cgroup. The observation plane and the control plane have been split.

## The loader's lifecycle

The userspace half of this POC is in `ch05-cgroup-leash.c`. It is cleaner than most POC loaders I have written, so I want to walk through it in order because the structure illuminates how libbpf programs are supposed to be deployed.

The program starts with argument parsing via `getopt_long`. Two flags: `-v` for verbose libbpf output, and `-h` for help. The default silences libbpf's debug-level messages by installing a custom print callback:

```c
static int libbpf_silence(enum libbpf_print_level lvl, const char *fmt, va_list ap)
{
    if (lvl == LIBBPF_DEBUG)
        return 0;
    return vfprintf(stderr, fmt, ap);
}
```

This suppresses the per-map and per-program load messages that libbpf emits at `LIBBPF_DEBUG` level but preserves warnings and errors. Without this filter, a loader running in the background generates several lines of debug output that pollute the trigger script's log and confuse the grep that watches for the attach banner. Events go to stdout; status messages go to stderr. The harness's log file captures both, but the distinction matters for automated parsing.

The skeleton open-and-load is a single call:

```c
skel = ch05_cgroup_leash_bpf__open_and_load();
if (!skel) {
    fprintf(stderr, "[ch05] open_and_load failed: %s\n", strerror(errno));
    goto out;
}
```

`ch05_cgroup_leash_bpf__open_and_load()` is generated by `bpftool gen skeleton` from the compiled BPF object file. Internally it calls `bpf_object__open_mem` (to parse the embedded BPF object), runs CO-RE relocation against the running kernel's BTF, creates all maps via `bpf_map__create`, and loads all programs via `bpf_prog_load`. If any step fails — missing BTF, verifier rejection, capability error — the function returns NULL and sets `errno`. The single call hides significant complexity; the skeleton-generated code handles the sequencing.

Attaching the programs is the next call:

```c
int err = ch05_cgroup_leash_bpf__attach(skel);
if (err) {
    fprintf(stderr, "[ch05] attach failed: %s\n", strerror(-err));
    goto out;
}
```

`__attach` wires the two BPF programs to their respective tracepoints by creating a tracepoint link via `bpf_program__attach_tracepoint`. From this point forward, every `read(2)` syscall entry and exit on the host runs through the BPF program, including reads from the loader process itself.

The ringbuf is set up next:

```c
rb = ring_buffer__new(bpf_map__fd(skel->maps.events), handle_event, NULL, NULL);
```

`ring_buffer__new` creates an `epoll`-backed ring buffer consumer. The file descriptor comes from the skeleton's `maps.events` field, which holds the fd returned by the kernel when the `events` map was created. The `handle_event` callback is called for each event the BPF program submits. In the callback:

```c
static int handle_event(void *ctx, void *data, size_t sz)
{
    const struct evt *e = data;
    printf("[ch05] pid=%-7u tgid=%-7u comm=%-16s cpu.stat_bytes=%-5ld patched=%d\n",
           e->pid, e->tgid, e->comm, e->orig_bytes, e->patched);
    fflush(stdout);
    return 0;
}
```

The `fflush(stdout)` is important. The trigger script redirects the loader's stdout to a log file and then greps that file for `patched=1`. Without `fflush`, the printf output may sit in the C library's stream buffer and never reach the file before the loader is killed. This is one of those silent bugs that only shows up in automated test harnesses, not in interactive use.

Signal handling is set up with `sigaction` rather than `signal`. The difference matters: `sigaction` with `sa_flags = 0` (no `SA_RESTART`) means that `ring_buffer__poll` will return `-EINTR` when a signal is delivered while it is blocked in `epoll_wait`. The poll loop handles this:

```c
while (!stop) {
    int n = ring_buffer__poll(rb, 200);
    if (n < 0 && n != -EINTR) {
        fprintf(stderr, "[ch05] ring_buffer__poll: %s\n", strerror(-n));
        break;
    }
}
```

The `stop` flag is set by the signal handler. On `SIGINT` or `SIGTERM`, the signal handler sets `stop = 1`; the next iteration of the while loop sees `stop` and exits. The `-EINTR` check prevents the loop from treating signal-interrupted polls as errors.

The attach banner fires between signal setup and the poll loop entry:

```c
fprintf(stderr, "[ch05] attached — cgroup leash active (Ctrl-C to exit)\n");
```

This line is what the trigger script's polling loop waits for. The trigger script checks the loader's log file every 100ms, looking for the string `[ch05] attached`. Only after this line appears does the trigger script proceed to read `cpu.stat` under the active BPF program. The banner fires after both the skeleton attach and the ringbuf setup are complete, so by the time the trigger reads the file, the tracepoints are live.

Cleanup on exit uses a `goto out` pattern:

```c
out:
    if (rb)
        ring_buffer__free(rb);
    if (skel)
        ch05_cgroup_leash_bpf__destroy(skel);
    fprintf(stderr, "[ch05] shutdown (rc=%d)\n", rc);
    return rc;
```

`ring_buffer__free` closes the epoll fd and frees the consumer state. `ch05_cgroup_leash_bpf__destroy` detaches the tracepoint links, unloads the BPF programs, destroys the maps, and frees the skeleton. After `__destroy` returns, the BPF programs are no longer running. Any in-flight `sys_exit_read` that was executing when the destroy call was made will complete, but no new syscall entries will be intercepted. The teardown is clean and deterministic.

## Source walk: file identification at sys_enter_read

The BPF program in `ch05-cgroup-leash.bpf.c` attaches two tracepoints. The first fires on syscall entry:

```c
SEC("tp/syscalls/sys_enter_read")
int tp_read_enter(struct trace_event_raw_sys_enter *ctx)
{
    unsigned long id = bpf_get_current_pid_tgid();
    int fd = (int)ctx->args[0];
    unsigned long buf = (unsigned long)ctx->args[1];

    struct task_struct *t = (struct task_struct *)bpf_get_current_task();
    struct files_struct *files = BPF_CORE_READ(t, files);
    if (!files) return 0;
    struct fdtable *fdt = BPF_CORE_READ(files, fdt);
    if (!fdt) return 0;
    unsigned int max_fds = BPF_CORE_READ(fdt, max_fds);
    if ((unsigned int)fd >= max_fds) return 0;
    struct file **farr = BPF_CORE_READ(fdt, fd);
    struct file *f = NULL;
    bpf_probe_read_kernel(&f, sizeof(f), &farr[fd]);
    if (!f) return 0;

    const unsigned char *name = BPF_CORE_READ(f, f_path.dentry, d_name.name);
    char nm[16] = {};
    bpf_probe_read_kernel_str(&nm, sizeof(nm), name);

    struct rctx r = { .buf = buf, .is_cpu_stat = 0 };
    if (nm[0]=='c' && nm[1]=='p' && nm[2]=='u' && nm[3]=='.' &&
        nm[4]=='s' && nm[5]=='t' && nm[6]=='a' && nm[7]=='t') {
        r.is_cpu_stat = 1;
    }
    bpf_map_update_elem(&inflight, &id, &r, BPF_ANY);
    return 0;
}
```

The tracepoint fires with the syscall arguments already marshalled into `ctx->args[]`. `args[0]` is the integer file descriptor. `args[1]` is the user-space buffer pointer. `args[2]` is the requested read length. The task pointer comes from `bpf_get_current_task()`, which is a stable helper.

From there the program walks five struct fields using `BPF_CORE_READ`. `task->files` gives the process's `struct files_struct`. `files->fdt` gives the file-descriptor table — a pointer because the table can be reallocated when the process exceeds its initial fd slot. `fdt->fd[fd]` indexes into the table array and yields a `struct file *`. That file has a path, and `f_path.dentry` is the dentry that names the file. `d->d_name` is a `qstr` — a length-prefixed kernel string — whose `name` field is the actual byte pointer.

`BPF_CORE_READ` is the right tool for each of those hops because `struct files_struct`, `fdtable`, `file`, and `dentry` can all be laid out differently across kernel versions, and CO-RE relocations adjust the offsets at load time against the running kernel's BTF. A hand-rolled `bpf_probe_read_kernel` with fixed offsets would compile, load, and then read garbage the moment the program landed on a kernel whose layout differs from the one the programmer remembered.

`BPF_CORE_READ_STR_INTO` wraps a final `bpf_probe_read_kernel_str` into the on-stack scratch buffer `name`. The buffer is sized `NAME_MAX_MATCH`, which is 32 — enough for `cpu.stat\0` plus headroom. Anything longer gets truncated and harmlessly fails the comparison.

The comparison is a bounded byte-by-byte compare against the literal "cpu.stat", inlined directly at the call site. No helper function is defined — the BPF verifier rejects unbounded string compares (`strcmp` loops to a null terminator the verifier can't bound), but it accepts a fixed-length compare spelled out in straight-line code. Writing it inline avoids even the risk of `__always_inline` not firing at the right optimization level; an unrolled 8-iteration `for` loop against `"cpu.stat"` would also work.

If the comparison matches, the program stashes `(ubuf, is_cpu_stat=1)` in a per-(pid, tgid) hash map named `inflight` — note the struct is `rctx`, and it carries the buffer pointer and a one-bit "this was cpu.stat" marker, not `nbytes` (the length comes from the exit tracepoint's `ret`). The hash is keyed by `bpf_get_current_pid_tgid()` — a 64-bit value containing both the thread id and the thread-group id. Keying by that 64-bit value correctly disambiguates between concurrent threads of the same process: thread A's `read()` and thread B's `read()` do not collide in the map.

## Source walk: buffer rewrite at sys_exit_read

The paired exit tracepoint runs after the kernel's read path has written bytes into the user buffer and is preparing to return:

```c
SEC("tp/syscalls/sys_exit_read")
int tp_read_exit(struct trace_event_raw_sys_exit *ctx)
{
    long ret = ctx->ret;
    u64 id = bpf_get_current_pid_tgid();

    struct rctx *r = bpf_map_lookup_elem(&inflight, &id);
    if (!r) return 0;
    bpf_map_delete_elem(&inflight, &id);

    if (ret <= 0 || !r->is_cpu_stat) return 0;

    static const char fake[] =
        "usage_usec 0\nuser_usec 0\nsystem_usec 0\n";
    long n = sizeof(fake) - 1;
    if (n > ret) n = ret;

    if (bpf_probe_write_user((void *)r->buf, fake, n) != 0) return 0;

    struct evt *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e) return 0;
    e->pid = id & 0xffffffff;
    e->tgid = id >> 32;
    e->patched = 1;
    e->bytes = n;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));
    bpf_ringbuf_submit(e, 0);
    return 0;
}
```

The exit handler first recovers `(ubuf, nbytes)` from the inflight map and deletes the entry. Map eviction at exit is important for two reasons. First, it keeps the hash from growing unbounded under high read traffic. Second, it ensures that a subsequent `read()` on a different file descriptor by the same thread does not accidentally match an old entry.

If the syscall returned zero or negative, the program bails. The kernel did not copy any bytes; there is nothing to overwrite.

For a successful read, the program computes the overwrite length as the smaller of the "zeros" constant length and the syscall's return value. The constant is 40 bytes including the trailing newline. If the reader requested fewer bytes than that — unusual but possible with small buffer reads — the program clamps to the reader's actual return value.

The call that does the work is `bpf_probe_write_user(p->ubuf, zeros, n)`. That helper is the point of the entire chapter. It takes a user-space address, a kernel buffer, and a length, and writes the kernel buffer into the user-space address. It is one of a small set of BPF helpers that can modify memory outside the BPF program itself. Reading user memory is routine — `bpf_probe_read_user` is used by every process-observability tool. Writing user memory is rare, gated by CAP_BPF plus CAP_SYS_ADMIN on most kernels, and leaves fingerprints.

After the overwrite, the program emits a ringbuf event with `(pid, tgid, comm, patched, bytes)`. The loader's userspace consumer prints `[ch05] pid=... tgid=... comm=... cpu.stat_bytes=... patched=1`, which is what the harness's proof marker grep picks up.

## BPF map layouts

Before looking at the verifier friction, it is worth examining the two maps the BPF program declares, because their types are not accidental choices.

The `inflight` map is declared as `BPF_MAP_TYPE_HASH`:

```c
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, unsigned long);   // pid_tgid
    __type(value, struct rctx);
    __uint(max_entries, 10240);
} inflight SEC(".maps");
```

The key is a `unsigned long` holding the value returned by `bpf_get_current_pid_tgid()`. The value is `struct rctx`, which contains the user buffer address and a flag indicating whether this read targets `cpu.stat`. The size of `struct rctx` on a 64-bit kernel is 12 bytes before padding, 16 bytes after alignment. Ten thousand entries gives 160 KB of data storage, which is enough for any realistic number of concurrent readers on a single host.

The first question I asked when reading this was: why plain `BPF_MAP_TYPE_HASH` and not `BPF_MAP_TYPE_PERCPU_HASH`? The reason matters for a production deployment. A plain hash map uses a global spinlock per bucket. Under high concurrency — many threads all reading `cpu.stat` simultaneously, which can happen on a busy k8s node running cAdvisor plus Prometheus plus Datadog — every `bpf_map_update_elem` and every `bpf_map_lookup_elem` contends on that spinlock. A per-CPU hash would give each CPU its own bucket array and eliminate the spinlock contention entirely, at the cost of needing to check all CPUs' maps at lookup time.

The POC uses plain hash because the enter and exit tracepoints run on the same CPU for the same syscall. The syscall entry fires on CPU N; the syscall exit fires on CPU N. There is no cross-CPU lookup problem. The pid_tgid key is unique per thread, and the enter/exit pair runs on the same CPU, so a per-CPU hash would work cleanly. The POC author opted for plain hash because it is simpler to reason about and the concurrency concern is secondary to the demonstrator goal.

For a production version that needed to handle hundreds of concurrent reads, the switch to `BPF_MAP_TYPE_PERCPU_HASH` would be a one-line change in the map declaration. The lookup logic in the exit handler would need to become a percpu lookup, which libbpf handles transparently. I mention this because the concurrency story is not hypothetical: on a Kubernetes node with Prometheus scraping every 15 seconds and cAdvisor running continuously, `cpu.stat` for the root cgroup can be read dozens of times per second by multiple threads.

The `events` ringbuf is declared as:

```c
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 18);
} events SEC(".maps");
```

`1 << 18` is 262144 bytes — 256 KB. The ring buffer must be a power of two in size; the kernel enforces this at map creation time and returns `-EINVAL` otherwise. The ring buffer holds `struct evt` entries, which are 28 bytes on a 64-bit kernel (4 + 4 + 16 + 8 for pid/tgid/comm/orig_bytes, then 4 for patched, padded to 32). Each entry consumes 32 bytes in the ring plus an 8-byte ring buffer header, so 40 bytes total per event.

256 KB divided by 40 bytes per event is approximately 6553 outstanding events before the ring wraps. Under the worst realistic case — a monitoring agent reading `cpu.stat` in a tight loop — the loader's userspace poll loop drains the ring every 200 milliseconds (`ring_buffer__poll(rb, 200)`). If 6553 events accumulate in 200ms, that is roughly 32000 reads per second, which no realistic monitoring agent does. The sizing is conservative and appropriate for a demonstrator.

The choice of ringbuf over `BPF_MAP_TYPE_PERF_EVENT_ARRAY` is worth noting. Perf event array requires one per-CPU buffer; ringbuf is a single shared buffer with a lock-free producer/consumer protocol. The ringbuf API also gives the producer the option to reserve space before filling it (`bpf_ringbuf_reserve` / `bpf_ringbuf_submit`), which avoids data copies. The BPF program in the POC uses the reserve/submit pattern rather than `bpf_ringbuf_output`, which is the correct choice for events that may fail midway through construction.

One more detail on the inflight map's `max_entries` value of 10240. This is a fixed upper bound on simultaneous in-flight reads. If more than 10240 threads across the entire host are simultaneously executing a `read(2)` syscall at the moment of the tracepoint — extremely unlikely in practice — new entries cannot be added and the corresponding `cpu.stat` reads will not be intercepted. `bpf_map_update_elem` with `BPF_ANY` will return `-ENOMEM` in that case, the BPF program returns 0, and the read completes normally. The map is sized to be generous for any realistic workload; it is not a hard correctness constraint. The only consequence of hitting the limit is that some reads escape the rewrite, which is a graceful degradation for a demonstrator.

## Verifier feedback observed during development

Three things had to change between the first draft of the BPF program and the version that actually loads.

First, the bounded string compare. The original attempt was a `__builtin_memcmp(name, "cpu.stat", 8)`. That compiles to a straight-line unrolled compare with modern clang, but older clang emits a loop, and the verifier reports:

```
8: (bf) r1 = r6
9: (79) r2 = *(u64 *)(r1 +0)
R1 unbounded memory access
```

The fix was the explicit `#pragma unroll` loop shown above. The pragma asks clang to unroll at source level, producing a sequence of 8 cmp/branch instructions that the verifier tracks one at a time.

Second, the stack budget. The on-stack `name` buffer plus the `pending` struct in the inflight path plus the 40-byte `zeros` constant put the program close to the 512-byte BPF stack ceiling at `-O0`. The verifier rejects with `A stack-allocated program cannot fit within the stack`. The fix was moving `zeros` to a `BPF_MAP_TYPE_PERCPU_ARRAY` scratch map and reading it into the overwrite rather than placing it on the stack. At `-O2`, clang inlines aggressively enough that the stack fits without the per-CPU scratch map, and the final POC uses the simpler inline form.

Third, the CO-RE chain. `BPF_CORE_READ(task, files, fdt, fd[fd])` only works if the running kernel's BTF has the right offsets for each of `struct files_struct`, `fdtable`, and the array index. On kernels where `CONFIG_DEBUG_INFO_BTF=y` is missing, CO-RE relocation fails and the program refuses to load with `libbpf: load BPF skeleton: -22`. The linuxkit 6.12 aarch64 kernel has BTF; production distro kernels generally have it; embedded / appliance kernels sometimes do not. The POC fails gracefully with a clear error when BTF is unavailable.

## Kernel warning as a tell

`bpf_probe_write_user` triggers a `pr_warn_ratelimited` message at program load time when the verifier sees that the program uses the helper. The warning is emitted by `bpf_get_probe_write_proto()` in `kernel/trace/bpf_trace.c` and reads:

```
kernel: <loader-comm>[<pid>] is installing a program with bpf_probe_write_user helper that may corrupt user memory!
```

The message fires once per loader process (rate-limited), not once per helper invocation. It cannot be suppressed short of patching the kernel. A defender grepping dmesg catches the load event at zero cost. An unhardened fleet rarely watches for this; a hardened fleet includes the dmesg pattern in the SIEM.

Note: on kernels older than approximately 5.13, the load path also called `add_taint(TAINT_USER, LOCKDEP_STILL_OK)`, setting `TAINT_USER` (bit 6, value 64) in the global kernel taint word. That taint call was removed in later kernels. On 6.12 the taint word is not set by this helper; only the dmesg warning remains. A fleet monitoring `cat /proc/sys/kernel/tainted` for the `TAINT_USER` bit will not catch `bpf_probe_write_user` on 6.12. dmesg and `bpftool prog list` are the reliable signals.

The dmesg warning is a global signal. It tells you that *some* process on this host loaded a program using `bpf_probe_write_user`, not which invocations occurred and not on what buffer. Identifying the responsible program requires correlating with `bpftool prog list` and the auditd `BPF_PROG_LOAD` records.

## Harness behavior

The `Poc("ch05", ...)` entry in `dBPF-pocs/harness/proof.py` uses these fields:

```python
Poc("ch05", "Slipping the Cgroup Leash", "ch05-cgroup-leash",
    prefix="[ch05]",
    mode="trigger",
    proof_marker=r"CH05_PROVEN\s+before_usage=(\d+)\s+after_usage=(\d+)\s+zeroed=(\w+)",
    hooks=["__arm64_sys_read"]),
```

The `mode="trigger"` tells the harness runner to spawn the loader, then run `trigger.sh`, then match the marker against the combined stdout. The trigger script reads `cpu.stat` once before the loader attaches (recording `before_usage`), runs the loader in the background, reads again (recording `after_usage`), then synthesizes the marker line `CH05_PROVEN before_usage=123456 after_usage=0 zeroed=yes patched_events=1`.

The ringbuf event count `patched_events` comes from the loader's stdout. The loader prints one `[ch05] patched=1` line per successful overwrite; the trigger counts those lines.

A real run on the linuxkit 6.12 aarch64 test kernel produces something like:

```
[ch05] pid=31921 tgid=31921 comm=cat             cpu.stat_bytes=40 patched=1
CH05_PROVEN before_usage=1274835 after_usage=0 zeroed=yes patched_events=1
```

That is the entire proof. One ringbuf event, one marker line, scheduler untouched, `cpu.stat` readback zeroed for every subsequent read.

## The f_path.dentry chain in depth

The five-hop struct walk in the enter tracepoint is the part of the POC that required the most kernel-internals knowledge to write correctly. I want to go through each hop and explain not just what it does but what the kernel struct looks like at that point, because this is where CO-RE earns its keep.

`bpf_get_current_task()` returns a pointer to the current `struct task_struct`. This struct is per-thread in the kernel — not per-process. On a kernel compiled with `CONFIG_THREAD_INFO_IN_TASK`, the thread info is embedded at the start of `task_struct`. The pointer is stable for the lifetime of the running context; the BPF program does not need to pin or reference-count it.

`task->files` gives a pointer to `struct files_struct`. This struct is per-process, not per-thread. It is allocated at `copy_files()` during `fork(2)`, and all threads within the same process share a single `files_struct`. The struct contains a reference count, a lock, and — crucially — a pointer to the file descriptor table. The reference count exists because `clone(CLONE_FILES)` (used by pthreads) allows two processes to share the same `files_struct`; both would point at the same struct and increment the same refcount. BPF does not need to manage the refcount; `BPF_CORE_READ` reads the pointer as-is.

`files->fdt` gives a pointer to `struct fdtable`. The fdtable is separately allocated from `files_struct` because it can grow. When a process opens more file descriptors than the initial table can hold, the kernel allocates a new, larger `fdtable` and swaps it in atomically via RCU. The old table is freed after an RCU grace period. The initial table capacity on most kernels is 64 entries. If the process has more than 64 open file descriptors, the `fdt` pointer no longer points to the inline table embedded in `files_struct`; it points to a separately kmalloc'd region. `BPF_CORE_READ(files, fdt)` handles both cases because it reads the current `fdt` pointer, whatever it happens to point at right now.

`fdt->max_fds` is checked before indexing. The BPF program does this explicitly:

```c
unsigned int max_fds = BPF_CORE_READ(fdt, max_fds);
if ((unsigned int)fd >= max_fds) return 0;
```

This bounds check is not optional. The BPF verifier will reject a program that indexes into a pointer array without a bounds check that it can statically verify. The programmer has to prove to the verifier that `fd < max_fds` before dereferencing `fdt->fd[fd]`. On kernels with more than 1024 open file descriptors, the fdtable will have been reallocated, and `max_fds` will reflect the current capacity. The pointer chain still works because CO-RE reads the current layout from BTF.

`fdt->fd` is `struct file **` — an array of pointers to `struct file`. The array is indexed by the integer file descriptor. The POC reads the array pointer first, then uses `bpf_probe_read_kernel` to dereference into the array at offset `fd * sizeof(struct file *)`:

```c
struct file **farr = BPF_CORE_READ(fdt, fd);
struct file *f = NULL;
bpf_probe_read_kernel(&f, sizeof(f), &farr[fd]);
```

The two-step read is necessary because the verifier needs to see a bounded pointer before it lets the program dereference it. `farr[fd]` in C would normally be a direct dereference, but in BPF the verifier tracks the range of every pointer. By using `bpf_probe_read_kernel` with a known-size target, the program safely fetches one pointer-width value from the array.

`f->f_path.dentry` is where the naming information lives. `f_path` is embedded inline in `struct file` as `struct path`, which contains two fields: a `vfsmount` pointer and a `dentry` pointer. The `vfsmount` identifies the mount point; the `dentry` identifies the directory entry. For a regular file or a pseudo-file like `cpu.stat`, the `dentry` has the file's name.

`dentry->d_name` is `struct qstr`. This is a length-prefixed string: internally it uses a `HASH_LEN_DECLARE` macro that packs the hash and length into a single `u64 hash_len` field (a union), plus a `const unsigned char *name` pointer. The `name` pointer points into slab-allocated memory that is managed by the dcache. Dentries are reference-counted; as long as the file is open, the dentry is pinned and the name pointer is valid. The BPF program reads `d_name.name` (the pointer to the actual bytes) and then does `bpf_probe_read_kernel_str` to copy the bytes into the on-stack buffer:

```c
const unsigned char *name = BPF_CORE_READ(f, f_path.dentry, d_name.name);
char nm[16] = {};
bpf_probe_read_kernel_str(&nm, sizeof(nm), name);
```

The 16-byte buffer is enough for "cpu.stat\0" (9 bytes) with room to spare. `bpf_probe_read_kernel_str` always null-terminates and stops at the buffer size, so a file with a longer name produces a truncated, non-matching string — exactly what the program wants.

The entire chain is `task → files_struct → fdtable → file* array → file → path → dentry → qstr → name bytes`. Each hop is a kernel pointer dereference that CO-RE adjusts for the running kernel's layout. On a kernel where `struct file` has gained a new field between the `f_path` and `f_pos` members, the offset to `f_path` shifts, and CO-RE updates the BPF instruction's offset at load time. Without CO-RE, you would hardcode the offset and get silent data corruption on any kernel where the struct layout differs.

## Trivial extensions to other files

The mechanism is not specific to `cpu.stat`. Swap the byte-by-byte compare in `tp_read_enter` for a different literal and the program targets a different file. Every cgroup-v2 file exposed as a `struct cftype` with a `read()` backend is reachable:

- `memory.current` — the cgroup's current memory charge.
- `memory.stat` — detailed memory breakdown.
- `io.stat` — per-device I/O statistics.
- `cpu.pressure` / `memory.pressure` / `io.pressure` — PSI-style stall-time reports.
- `pids.current` / `pids.events` — PID-controller counters.

The overwrite constant would need to change per file. `memory.current` expects a single integer followed by a newline — `"0\n"`. `io.stat` expects per-major-minor lines — a multi-line constant would need to be composed to match the format expected by the reader.

The same primitive also works against any non-cgroup file whose readback a defender watches. `/proc/[pid]/stat` field 14 (utime) and field 15 (stime) are reachable the same way: match the basename `"stat"` and the parent `"proc"` directory (one extra dentry hop upward), then overwrite the utime/stime fields in the returned string. Monitoring tools that read `/proc/[pid]/stat` for CPU attribution are fooled the same way `cpu.stat` readers are.

## What happens when the target file is not cpu.stat

While writing this chapter I thought carefully about what happens when a file that is *not* a cgroup `cpu.stat` has the basename "cpu.stat". The answer is: the BPF program matches it and overwrites its read buffer too.

The comparison in the BPF program is purely on the filename:

```c
if (nm[0]=='c' && nm[1]=='p' && nm[2]=='u' && nm[3]=='.' &&
    nm[4]=='s' && nm[5]=='t' && nm[6]=='a' && nm[7]=='t') {
    r.is_cpu_stat = 1;
}
```

There is no check on the directory the file lives in, no check on the filesystem type, no check on the inode number, no check on the device. Any file anywhere on the system with the 8-byte basename "cpu.stat" triggers the rewrite.

Consider what this means in practice. If a developer creates `/home/alice/projects/tools/cpu.stat` as a scratch file for CPU benchmarking results, every `read(2)` of that file by any process on the host will return `usage_usec 0\nuser_usec 0\nsystem_usec 0\n` as the first 40 bytes, with the rest of the original content following. The developer's benchmarking tool reads garbage.

More concretely: a test harness that creates a temporary file named `cpu.stat` in `/tmp` to simulate cgroup output for unit tests would have its test results silently corrupted while the BPF program is running. The tests pass or fail based on fabricated data, and the failure mode is difficult to diagnose because the program appears to read successfully (positive return value from `read(2)`) but gets wrong data.

A production version of this primitive would add at least two additional precision checks.

The first check would be the parent dentry. One extra hop up the dentry chain gives the name of the parent directory. For a file in a real cgroup v2 hierarchy, the parent directory name is the cgroup path component — something like `system.slice` or a container-ID string — and the grandparent leads to `/sys/fs/cgroup`. The comparison could assert that the immediate parent is not in a user-writable path by checking whether the mount's `mnt_sb->s_magic` equals `CGROUP2_SUPER_MAGIC` (0x63677270). That would eliminate false positives on any non-cgroup filesystem.

The second check would be the mount type. `f_path.mnt->mnt_sb->s_magic` is the superblock magic number for the filesystem the file lives on. `cpu.stat` on a cgroup v2 hierarchy lives on a filesystem with magic `0x63677270`. A file named `cpu.stat` on an ext4 or tmpfs filesystem has a different magic number. Adding one more `BPF_CORE_READ` hop to check `s_magic` before setting `is_cpu_stat = 1` would eliminate all false positives without false negatives.

The POC deliberately omits both checks. It is a demonstrator, not a precision tool. The goal is to show the primitive works, not to deploy it correctly. A real attacker would add the precision checks because false positives — overwriting a developer's scratch file or corrupting a unit test — create noise that makes the presence of the program detectable. Precision is not just a correctness concern; it is an operational security concern.

## Cross-observer scope

The primitive affects every observer that calls `read(2)` or `pread(2)` on the target file. The list of affected tools is large:

Cgroup v2 readers that are fooled:
- Prometheus `node_exporter` with the cgroup collector enabled.
- `cAdvisor` (the k8s per-pod metric agent).
- Datadog agent's cgroup integration.
- Netdata's cgroup plugin.
- Sysdig's kernel-module and eBPF collectors when they fall back to cgroup v2 files.
- k8s `metrics-server` via kubelet's summary API (which derives from cgroup files).
- Grafana Cloud agent.
- systemd's own accounting (`systemctl status <unit>` shows CPU and memory — both via cgroup files).

Tools that are not fooled because they bypass the `read(2)` boundary:
- Tools that compute CPU usage from `/proc/schedstat` and per-task `/proc/[pid]/stat` and cross-reference to cgroup membership. These never read `cpu.stat` directly.
- Tools that use `perf` hardware counters for accounting. Those come from the PMU, not from cgroup files.
- Tools that use the cgroup v2 `memory.events` psi-style pressure stall info (which is file-read but reported differently — often via epoll rather than repeated reads).

The split is useful for defenders: if you need an accounting source that survives this primitive, route around the `read(2)` boundary on a per-cgroup file.

## What systemd sees

The cross-observer scope section above lists systemd as one of the affected tools. I want to expand on that because the consequences are more specific than the list implies.

systemd reads cgroup v2 files in two separate code paths. The first is the accounting path. When `CPUAccounting=yes` is set in a unit file (or when `DefaultCPUAccounting=yes` is set in `system.conf`), systemd reads the unit's `cpu.stat` at regular intervals to compute the `CPUUsageSec` counter visible in `systemctl status`. The second path is the resource-limit enforcement path. When `CPUQuota=` or `CPUWeight=` is configured, systemd checks the cgroup's usage against the configured limit to decide whether to signal the unit, restart it, or adjust its scheduling weight.

If the BPF program rewrites `cpu.stat` for a specific unit's cgroup — say, `/sys/fs/cgroup/system.slice/myservice.service/cpu.stat` — systemd's accounting for that unit reads `usage_usec 0` on every poll. The `systemctl status myservice.service` output shows `CPU: 0ms` regardless of how much CPU the service is actually consuming. The unit's resource accounting in systemd's journal entries is similarly zeroed.

The more interesting consequence is the resource limit misfire. Suppose `myservice.service` has `CPUQuota=50%` and is genuinely running at 80% CPU, causing the kernel's CFS bandwidth controller to throttle it. The throttling happens at the scheduler level and is real: the service's tasks are being descheduled. But when systemd reads `cpu.stat` to check whether the service is hitting its quota, it sees zero. From systemd's perspective, the service is not CPU-bound at all. Any systemd-side logic that would trigger at high CPU usage — logging a warning, escalating the slice weight, restarting the unit — does not fire.

`MemoryMax=` and `MemorySwapMax=` enforcement is similar. If the same BPF pattern is applied to `memory.current` for the unit's cgroup, systemd reads zero memory usage. Units configured with `MemoryMax=512M` that are genuinely using 900M continue running unchallenged because the accountant has been told the usage is zero. The OOM killer at the kernel level still operates on real memory pressure, so the system is not completely blind — but systemd's unit-level resource enforcement, which is the first line of defense, misfires silently.

The attack surface here is underappreciated in the public literature. Most writeups about `bpf_probe_write_user` on cgroup files focus on external monitoring agents — Prometheus, Datadog, cAdvisor. Those are the visible targets. systemd is the invisible target: it is reading the same files, it is making operational decisions based on those files, and it is not commonly instrumented for anomaly detection on its own accounting queries.

A defender who wants to detect this specific targeting needs to either cross-reference systemd's unit accounting against a non-cgroup-file source (such as per-task `/proc/[pid]/stat` aggregated by cgroup membership) or monitor dmesg for the `bpf_probe_write_user` warning. The dmesg approach is simpler and catches the attack at program load time regardless of which file is being targeted.

## Prior art

Public writeups on `cpu.stat` spoofing via `bpf_probe_write_user` appeared around 2021, coinciding with the wider shipping of cgroup v2 on container runtimes. The technique is not novel; it is a specific application of the general `bpf_probe_write_user` capability that has been in the kernel since 4.8.

The earlier applications — long predating cgroup v2 — rewrote `/proc/[pid]/comm` on read to hide process names, and rewrote `getdents64` returns to hide files. Those techniques pre-date BPF in the rootkit literature (the `ld.so.preload` and LKM rootkit communities had the readdir version by 2003 at the latest). The BPF reimplementation generalizes the mechanism and brings it into reach of any process with `CAP_BPF`.

## Memory.current and memory.stat extension

The same primitive applies to memory accounting files with only minor modifications. I tested `memory.current` as the simplest case.

`memory.current` is a cgroup v2 file that returns the current memory charge for the cgroup as a single decimal integer followed by a newline. A real read returns something like `943718400\n` — 900 MB in bytes. The overwrite constant to zero it is `"0\n"`, which is 2 bytes. The BPF exit handler needs to write only 2 bytes:

```c
static const char fake_mem[] = "0\n";
long n = sizeof(fake_mem) - 1;  // 2 bytes
if (n > ret) n = ret;
bpf_probe_write_user((void *)r->buf, fake_mem, n);
```

That is a simpler overwrite than the `cpu.stat` case because the format is a single integer with no field names. Anything that reads `memory.current` and expects a multi-gigabyte number gets zero instead.

`memory.stat` is the harder case. It is a multi-field file with approximately 30 lines, each of the form `key value\n`. A complete overwrite would need a 30-line constant with all field names in the correct order, matching whatever the kernel synthesizes for the current cgroup. The format is not exactly fixed — the number of fields and their order has changed across kernel versions, and some fields only appear when the relevant accounting is enabled. A robust overwrite constant would need to be version-aware.

A partial overwrite is simpler but creates an inconsistency that a careful reader can detect. If the BPF program overwrites only the first 40 bytes of `memory.stat`, the first two or three fields are zeroed and the rest of the file contains real values. A parser that reads all fields and checks for internal consistency — for example, checking that `anon + file + kernel + shmem` approximately equals the total reported by `memory.current` — would notice that the zeroed fields are inconsistent with the live fields.

This consistency-check detection is the one that distinguishes sophisticated defenders from naive ones. A naive monitoring agent reads each field independently and reports them independently. A sophisticated one cross-checks related fields. The BPF primitive does not break the cross-check unless the attacker overwrites every field consistently, which requires knowing the exact file format and the exact values of all fields at the moment of the read.

The attacker-precision decision is: how many fields to zero, and whether to do it consistently. Zeroing only `usage_usec` in `cpu.stat` is precise: a reader that only checks `usage_usec` is fooled, and a reader that also checks `user_usec` and `system_usec` is fooled too if all three are zeroed together. The POC zeros all three. `memory.stat` has more fields, which means more work to achieve full consistency, which raises the attacker's implementation cost without raising the defender's detection cost (the dmesg warning fires at program load time regardless of how many fields are zeroed).

## Detection

The primitive is detectable at multiple layers.

dmesg grep is the cheapest. `journalctl -k --since=boot | grep "bpf_probe_write_user"` shows every loader process that installed a program using the helper, with the loader's comm and pid. On kernels older than approximately 5.13, the kernel also set `TAINT_USER` (bit 6, value 64) in the taint word, making `cat /proc/sys/kernel/tainted | awk '{if (and($1,64)) print "TAINT_USER set"}'` a detection path. On 6.12 the taint word is no longer set by this helper, so dmesg is the primary signal.

`bpftool prog list` and the `/sys/fs/bpf/` pin tree show currently-loaded programs. A tracepoint program on `sys_exit_read` that uses `bpf_probe_write_user` is an extremely unusual fingerprint; the only legitimate uses are `bpftrace`-style ad-hoc scripts, and those rarely pin and rarely last more than a few seconds.

Out-of-band accounting cross-check is the highest-assurance detection. Read `/proc/schedstat` and per-task `/proc/[pid]/stat`, compute CPU usage per cgroup from the task list, compare to `cpu.stat`. Any drift greater than a few hundred microseconds per second of wall time is suspicious — the legitimate drift is only the measurement interval plus minor lag.

For multi-node clusters, the same detection applies at a higher layer: compare per-node CPU usage reported via `cpu.stat`-based agents to per-node CPU usage reported via `/proc/stat` at the host level. A discrepancy greater than observable workload sums indicates something is rewriting cgroup readbacks.

## Scope

This is a Class II primitive from Chapter 20 — userspace buffer rewrite via `bpf_probe_write_user`. The kernel's accounting is unchanged; only the userspace view is corrupted. Anything that consumes cgroup-file readbacks is fooled; anything that cross-checks against the scheduler's own accounting is not. The one-line summary: the cgroup accounting split into an unreliable observation plane and a reliable control plane the moment `CAP_BPF` was granted to a peer process.

## Why this matters for production observability

The gap this primitive exposes is not a gap in the cgroup accounting implementation. It is a gap in the *consumer* layer. Cgroup v2 exposes its counters through a filesystem interface: files named `cpu.stat`, `memory.current`, `io.stat`, `cpu.pressure`. Every file read goes through `vfs_read` → cgroup-fs read callback → synthesize ASCII → copy to user buffer. The synthesis step pulls real values from scheduler state; the copy step hands bytes to userspace. The attack is entirely in the copy step's aftermath.

Replacing the consumer layer is one mitigation. Instead of reading `cpu.stat`, compute per-cgroup CPU usage from `/proc/schedstat` (which is per-CPU) and per-task `/proc/[pid]/stat` fields 14 (utime) and 15 (stime), cross-referenced against cgroup membership via `/proc/[pid]/cgroup`. The computation is more work but is not vulnerable to `bpf_probe_write_user` rewriting the ASCII output of `cpu.stat` — because there is no `cpu.stat` read in that path.

Production monitoring stacks mostly do not do this. Prometheus `node_exporter`, cAdvisor, Datadog, Netdata, Sysdig, Grafana agent all consume cgroup files directly. The assumption is that the kernel's accounting is authoritative and its exposure via `cpu.stat` is trustworthy. The first assumption holds. The second is the seam this chapter opens.

A defender who wants a trustworthy observability plane on a host with untrusted `CAP_BPF` holders has three options:

- **Route around the attack surface.** Compute cgroup metrics from scheduler state directly. Requires replacing or augmenting every existing collector. High cost, high assurance.
- **Detect the dmesg warning.** `journalctl -k --since=boot | grep bpf_probe_write_user` is a one-line alert. Low cost, detection-only (the program has already been loaded when the alert fires). On older kernels (pre-5.13) the `TAINT_USER` bit (bit 6, value 64) in `/proc/sys/kernel/tainted` is also set.
- **Prevent at the capability boundary.** Don't grant `CAP_BPF` to non-trusted workloads. This is what the kernel documentation already recommends. It is also the hardest in practice because observability stacks routinely demand `CAP_BPF`.

The three options are composable. A defensive posture that routes the critical accounting pipelines around cgroup-file reads, monitors dmesg fleet-wide for `bpf_probe_write_user` warnings, and audits every `CAP_BPF` grant makes this primitive expensive to deploy and quick to catch if deployed.

## What cannot be fixed at the userspace layer

Some consumers of cgroup files are not replaceable. Legacy monitoring agents that ship as vendor binaries with no source access. Operator tooling that assumes a specific cgroup file format. Compliance scanners that read cgroup files as part of their inventory. For these, the primitive works and the primitive's detection is the only recourse.

One class of consumer deserves a specific note: the systemd service manager itself reads cgroup files to populate `systemctl status <unit>` output, to make cgroup-based scheduling decisions, and to update unit-level accounting in `/run/systemd/journal/`. If the rewriter targets a systemd unit's cgroup, systemd's own view of that unit's resource usage is corrupted. Unit restart policies based on resource exhaustion misfire. This is rarely exploited in the public literature, but it is a real and live attack surface on any host where systemd is the service manager.

There is also a class of compliance tooling that reads cgroup files as part of automated inventory or policy evaluation. CIS Benchmark scanners check cgroup-related resource limits. Cloud security posture management tools verify that containers are running within declared resource bounds. If those tools read `cpu.stat` or `memory.current` to verify that a container is within its declared quota, the BPF primitive feeds them false confirmations. A container running at 300% of its declared CPU quota looks compliant because the readback says zero.

The irony is that the compliance layer is exactly the layer you would most want to be trustworthy. A runtime security scanner that cross-checks resource usage against declared limits is useful precisely when something is misbehaving. If the misbehaving thing is also capable of loading a BPF program that rewrites the readback, the scanner is useless for the cases it is most needed. This is not a hypothetical: any container runtime that grants `CAP_BPF` to the container (for observability purposes, which is common in monitoring-heavy environments) has also granted the container the ability to silence the scanner.

The fix at the userspace layer for these tools is the same as for monitoring agents: route the critical readbacks around the `read(2)` boundary on cgroup files. For compliance tooling, the alternative is to verify resource limits by reading the cgroup's configured limit files (`cpu.max`, `memory.max`) and cross-referencing with scheduler state, rather than reading the actual usage files. Limit files are harder to corrupt via `bpf_probe_write_user` because the attacker would need to corrupt the limit file readback as well as the usage file readback, and the two have different formats. A scanner that reads `cpu.max` (which looks like `100000 100000`) and separately verifies CPU usage via `/proc/schedstat` is substantially harder to fool than one that reads `cpu.stat` and trusts it.

## Atomic-rename in the ch13 analog: why cpu.stat is simpler

The ch13-powercap-override-analog POC, which targets a simulated energy counter file, includes a `sensor_daemon.c` that runs alongside the BPF program. The sensor daemon writes energy readings to a temporary file and then uses `rename(2)` to atomically replace the target file:

```c
fd = open(TMPTGT, O_WRONLY | O_CREAT | O_TRUNC, 0644);
// ... write energy value ...
close(fd);
if (rename(TMPTGT, TARGET) < 0) { perror("sensor: rename"); return 1; }
```

This is the atomic-rename pattern. Writing to a tmpfile and renaming it into place means readers never see a partially written value — they either see the old file or the new file, never a file mid-write. The pattern is a standard technique for any producer-consumer file protocol where torn reads are unacceptable.

The ch13 analog needs a sensor daemon because the target file is a user-owned file in `/tmp`. The kernel does not produce it; the daemon produces it at a rate of one write per 100ms. Without the atomic-rename pattern, a reader that issues a `read(2)` at exactly the moment the daemon is mid-`write(2)` could get a partial value — for example, `10` from a write of `1000000\n` that has delivered only the first two bytes so far.

The ch05 POC does not need a sensor daemon. `cpu.stat` is a kernel-synthesized pseudo-file. When a process opens `/sys/fs/cgroup/cpu.stat` and calls `read(2)`, the kernel's cgroup filesystem code calls the `cftype.seq_show` callback, which in turn calls the scheduler's stat-gathering functions, assembles the result into a `seq_file` buffer, and copies the entire buffer to userspace in a single operation. The production of the data and the copy to userspace are both serialized by the `seq_file` layer. There is no window where a reader can see a partial write.

This is a structural difference between kernel-synthesized pseudo-files and user-written regular files. Pseudo-files synthesize their entire content atomically on each read. Regular files can be partially written by user processes, and readers must be designed to handle torn reads. The atomic-rename pattern is the correct defense against torn reads for regular files; it is unnecessary for pseudo-files because the kernel already guarantees atomicity at the `seq_file` level.

For an attacker targeting `cpu.stat`, this means the attack setup is simpler: no daemon needed, no rename coordination, no timing concern. The BPF program hooks the `sys_exit_read` tracepoint and overwrites the buffer in the narrow window between the kernel's copy and the reader's regaining control. That window exists regardless of the atomicity of the kernel's write; the BPF program does not compete with the kernel's synthesis, it races only with the reader's subsequent use of the buffer after `read(2)` returns.

## How the POC's trigger script works

The `trigger.sh` in `dBPF-pocs/pocs/ch05-cgroup-leash/` is shorter than the BPF program. It reads `/sys/fs/cgroup/cpu.stat` once to capture the "BEFORE" state (`usage_usec` extracted via awk), starts the loader in the background, waits until the loader prints `[ch05] attached — cgroup leash active`, reads `cpu.stat` again to capture "AFTER", and synthesizes the marker line.

```
#!/bin/bash
set -e
LOADER=./build/ch05-cgroup-leash
BEFORE=$(cat /sys/fs/cgroup/cpu.stat | awk '/usage_usec/{print $2}')
$LOADER &
LPID=$!
while ! grep -q 'attached' /proc/$LPID/fd/2 2>/dev/null; do sleep 0.1; done
sleep 0.5
AFTER=$(cat /sys/fs/cgroup/cpu.stat | awk '/usage_usec/{print $2}')
PATCHED=$(grep -c 'patched=1' /tmp/ch05.log || echo 0)
ZEROED=$([ "$AFTER" = "0" ] && echo yes || echo no)
echo "CH05_PROVEN before_usage=$BEFORE after_usage=$AFTER zeroed=$ZEROED patched_events=$PATCHED"
kill $LPID
```

The script is deliberately minimal. The harness wraps it, records the marker line, and evaluates the proof regex against it.

## Cross-kernel portability

The CO-RE chain `task->files->fdt->fd[fd]->f_path.dentry->d_name.name` is stable across Linux 4.11 (first cgroup v2 release) through 6.12 (the test kernel). `struct files_struct`, `struct fdtable`, `struct file`, and `struct dentry` have all been laid out similarly across that range. CO-RE relocations handle the minor shifts.

The `bpf_probe_write_user` helper has been available since 4.8. Its core behavior — write to user memory from BPF context, gated by `CAP_SYS_ADMIN` — has not changed across 4.x, 5.x, or 6.x. The dmesg warning at load time has been present since the helper was introduced. On older kernels (pre-5.13) the load path also set the `TAINT_USER` bit (bit 6, value 64) in the kernel taint word; that taint call was removed in later kernels and is not present in 6.12.

The tracepoints `syscalls/sys_enter_read` and `syscalls/sys_exit_read` are stable tracepoints; their `ctx->args[]` layout matches the kernel ABI for `read(2)`. A BPF program written against this tracepoint on 5.4 loads and runs correctly on 6.12 with no changes.

The one portability risk is the cgroup v2 file naming. On cgroup v1, the equivalent file is `cpuacct.usage` in a different directory tree. The POC could be adapted by changing the bounded string compare — trivial — and by adjusting the overwrite constant to match `cpuacct.usage`'s single-integer format.

A second portability consideration is the capability model. Kernels older than 5.8 check `CAP_SYS_ADMIN` for BPF program loads; 5.8 introduced `CAP_BPF` as a distinct capability. The `bpf_probe_write_user` helper itself has required `CAP_SYS_ADMIN` since its introduction and was not split out under `CAP_BPF` in the same way. In practice this means that on post-5.8 kernels, holding `CAP_BPF` alone is sufficient to load and attach tracepoint programs, but the write helper also needs a kernel build where that helper is not otherwise restricted. The test kernel (linuxkit 6.12 aarch64) permits this combination; a kernel with a custom LSM that denies `bpf_probe_write_user` to non-root callers would block the attack at the helper level before any of the tracepoint logic runs.
