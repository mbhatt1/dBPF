ACPI WSMI Ping: Subverting Hardware Management Interfaces

Wut

A compact exploration of how eBPF can twist the kernel feature “ACPI WSMI Ping” into an attack primitive—maintaining verifier legality while undermining isolation. This technique allows attackers to communicate with hardware management interfaces directly, bypassing standard security controls.

Why

Because eBPF + misconfiguration => broken isolation. The ACPI WSMI interface provides a direct communication channel to hardware that bypasses many security controls. When combined with eBPF’s ability to hook into kernel functions, this creates a powerful attack vector that can be difficult to detect and mitigate.

Attacker hat on

  1. Identify a target system with ACPI WSMI interfaces exposed
  2. Develop an eBPF program that hooks into ACPI call paths
  3. Load the malicious BPF program with appropriate privileges
  4. Trigger the exploit by sending specially crafted ACPI commands
  5. Gain persistent access through hardware management interfaces
  6. Exfiltrate data or maintain control even through OS reinstalls

Defender hat on

  1. Remove CAP_BPF from untrusted containers and processes
  2. Implement strict BPF LSM policies to restrict eBPF program loading
  3. Monitor ACPI interface usage for anomalous patterns
  4. Apply firmware updates that restrict WSMI functionality
  5. Use hardware security modules (HSMs) to validate firmware integrity
  6. Implement defense-in-depth strategies that don’t rely solely on OS-level controls

Conclusion

eBPF is all you need. The combination of eBPF’s powerful hooking capabilities with direct hardware interfaces like ACPI WSMI creates attack vectors that transcend traditional security boundaries. This highlights the importance of treating eBPF as a privileged capability that requires strict access controls and monitoring.

Technical Details

ACPI WSMI Interface Overview

The ACPI (Advanced Configuration and Power Interface) WSMI (Windows System Management Interface) provides a mechanism for the operating system to communicate with system firmware and hardware components. Originally designed for Windows systems, these interfaces are also present in Linux kernels to maintain hardware compatibility.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that handle ACPI requests. By intercepting these calls, an attacker can:

  1. Intercept legitimate ACPI calls: Hook into acpi_evaluate_object() or related functions
  2. Modify ACPI method parameters: Change parameters of legitimate calls or inject entirely new calls
  3. Bypass access controls: Execute privileged operations that would normally be restricted
  4. Establish persistence: Modify firmware settings that survive OS reinstallation

// Simplified eBPF program to hook ACPI calls
SEC("kprobe/acpi_evaluate_object")
int BPF_KPROBE(hook_acpi_evaluate, struct acpi_object_list *parameters)
{
    // Check if this is a WSMI call we want to intercept
    if (parameters && parameters->count > 0) {
        struct acpi_object *obj = parameters->pointer;
        
        // Modify parameters for our malicious purposes
        if (obj && obj->type == ACPI_TYPE_STRING) {
            // Inject our payload
            bpf_probe_read_str(&obj->string.pointer, 
                               sizeof(MALICIOUS_COMMAND), 
                               MALICIOUS_COMMAND);
        }
    }
    
    return 0;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attaching to ACPI-related functions
  • Unusual patterns of ACPI method calls
  • Discrepancies between expected and actual hardware behavior
  • Unexpected firmware or SMM (System Management Mode) activity

This technique demonstrates why proper eBPF restrictions are critical for maintaining system security, especially in environments where hardware isolation is a key security requirement.
