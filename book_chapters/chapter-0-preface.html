Chapter 0: The Dark Side of BPF

January 1st, 2025 - Lab Notes

Alright, let’s talk about what you’re really getting into here. This isn’t your typical security research where we find bugs and write CVEs. This is something way more interesting—and frankly, way more powerful.

I started playing with eBPF for legitimate observability work. Syscall tracing, network monitoring, the usual stuff. But the deeper I got into the architecture, the more I realized we’re dealing with something completely different from traditional attack surfaces.

What Makes This Different

eBPF gives you direct kernel code injection with ring-0 privileges. Every technique in this manual exploits this by design:

  • Kernel function hooking: Direct interception of security decision points
  • Runtime code modification: Altering kernel behavior without recompilation
  • Privilege boundary bypass: Operating below traditional security layers
  • Real-time system manipulation: Modifying live kernel state

Here’s the kicker: eBPF doesn’t break security mechanisms—it operates at a layer where those mechanisms simply don’t apply.

The Attack Surface

Traditional security assumes the kernel behaves predictably. eBPF throws that assumption out the window:

Capability System: cap_capable() decisions can be intercepted and modified in real-time Seccomp Filters: BPF programs execute before seccomp evaluation in the syscall path LSM Framework: Security hooks can be influenced by eBPF programs attached to the same functions Audit Subsystem: Event generation and routing can be manipulated at the kernel level

What You’ll Learn

This manual covers three categories of kernel manipulation:

System-Level Bypasses: Security controls, container isolation, resource limits Kernel-Level Manipulation: Process management, filesystem operations, network stack Hardware-Level Access: Interrupt handling, power management, device control

Every technique leverages eBPF’s legitimate kernel programming interface. No vulnerabilities, no exploits—just intended functionality used for purposes the developers probably didn’t anticipate.

Technical Requirements

All techniques require:

  • CAP_BPF or CAP_SYS_ADMIN capabilities
  • eBPF program loading permissions
  • Understanding of kernel internals and eBPF helper functions

The code examples use libbpf and demonstrate real working implementations. No theoretical bullshit—everything here actually works.

Defense Implications

Mitigation strategies focus on:

  • eBPF capability restriction and monitoring
  • BPF LSM policy implementation
  • External validation of kernel behavior
  • Hardware-based security enforcement

But here’s the fundamental challenge: when the kernel itself becomes programmable, traditional security boundaries become suggestions rather than hard limits.

Why This Matters

We’re not just talking about new attack techniques. We’re talking about a fundamental shift in how computing systems work. When everything becomes programmable—including the security mechanisms themselves—the entire threat model changes.

“eBPF isn’t a vulnerability—it’s a feature that makes every other security mechanism optional.”
