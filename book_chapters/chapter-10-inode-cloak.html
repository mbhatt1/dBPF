Chapter 10: Inode Cloak

Making Files Invisible to Detection Systems

February 10th, 2025 - The Vanishing Act

After creating process doppelgängers yesterday, I was fascinated by the concept of identity manipulation. But processes aren’t the only things with identities in the kernel—files have them too. Every file has an inode, a unique identity that the filesystem uses to track it.

What if I could make files invisible? Not just hidden with a dot prefix, but truly invisible to detection systems, file integrity monitors, and security scanners?

Today I learned to make files vanish into thin air while keeping them fully functional.

The File Identity System

I spent the morning studying inodes—the kernel’s file identity system. They’re designed to:

  • Uniquely identify files within a filesystem
  • Track file metadata like permissions, timestamps, and ownership
  • Enable file operations by providing a consistent reference point
  • Support security monitoring by giving each file a trackable identity

It’s like having a social security number for every file—a unique identifier that follows the file throughout its lifetime and enables all sorts of tracking and monitoring.

But what if I could make files exist without proper identification?

My Invisibility Strategy

The idea was elegant in its simplicity. Instead of trying to hide files from specific tools, I would make them invisible at the filesystem level itself.

My plan:

  1. Hook inode lookup functions - Intercept the mechanisms that resolve file paths to inodes
  2. Create selective blindness - Make certain files invisible to specific processes or tools
  3. Maintain functionality - Keep the files fully accessible to authorized processes
  4. Evade detection - Make file integrity monitors and security scanners unable to see the files

The Night I Made Files Disappear

I’ll never forget the first time I pulled it off. I had created a test file that should have been visible to all the standard file listing and security scanning tools.

I loaded my eBPF program to hook into the inode lookup functions. Then I configured it to make my test file invisible to specific processes while keeping it visible to others.

It worked. The file was completely invisible to ls, find, file integrity monitors, and security scanners. But my authorized processes could still read and write to it normally.

The Perfect Hiding Place

The beautiful part was that the file wasn’t just hidden—it was truly invisible at the filesystem level. Security tools couldn’t see it, backup systems couldn’t find it, and file integrity monitors couldn’t track it. But it was still there, fully functional, waiting for authorized access.

I had created the perfect hiding place—files that existed in plain sight but were invisible to anyone looking for them.

The Techniques I Perfected

Over the following days, I developed several file invisibility techniques:

Selective Visibility: Making files visible only to specific processes Tool-Specific Hiding: Making files invisible to security scanners while visible to normal operations Conditional Existence: Making files appear and disappear based on context Metadata Manipulation: Altering file metadata to confuse detection systems Path Obfuscation: Making file paths resolve differently for different processes

Each technique exploited the fundamental assumption that files have consistent, observable identities.

The Broader Implications

This wasn’t just about hiding files—I had discovered that the fundamental assumptions of file system integrity could be violated. When you can make files invisible:

  • Hide malware from antivirus scanners and security tools
  • Evade file integrity monitoring by making critical files untrackable
  • Store sensitive data in files that backup systems can’t see
  • Establish persistence through files that system administrators can’t find

I had broken the basic assumption that files have consistent, observable existence.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to filesystem functions
  • Implement external file monitoring that doesn’t rely on kernel reporting
  • Use hardware-based file integrity checking
  • Deploy multiple independent file tracking systems

But I had discovered something fundamental: when you can manipulate file visibility at the kernel level, traditional file system security becomes meaningless.

The Master of Invisibility

I had become a master of invisibility, capable of making files vanish into thin air while keeping them fully functional. The filesystem, supposedly providing reliable file tracking and integrity, had become my personal magic show.

The files were there, but nobody could see them.

“I had created the perfect hiding place—files that existed in plain sight but were invisible to anyone looking for them.”
