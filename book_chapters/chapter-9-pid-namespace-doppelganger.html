Chapter 9: PID Namespace Doppelgänger

Creating Process Doppelgängers Across Namespaces

February 9th, 2025 - The Identity Crisis

After yesterday’s keyring heist, I was riding high on my success. But there was something that had been bothering me about process isolation. Containers rely on PID namespaces to keep processes separate—each container thinks it has its own process space, its own PID 1, its own isolated world.

But what if I could create process doppelgängers—processes that exist in multiple namespaces simultaneously, or processes that appear to be something they’re not?

Today I learned to bend the very concept of process identity.

The Identity System

I spent the morning studying PID namespaces—the kernel’s identity management system for processes. They’re designed to:

  • Isolate process trees so containers can’t see each other’s processes
  • Provide clean PID spaces where each container starts with PID 1
  • Enforce security boundaries between different process groups
  • Enable process monitoring within isolated environments

It’s like having separate apartment buildings where residents can’t see into other buildings, and each building has its own numbering system starting from 1.

But what if I could create a process that appears to live in multiple buildings at once?

My Doppelgänger Strategy

The idea was mind-bending but achievable. Instead of accepting the PID namespace boundaries, I would create processes that could exist in multiple identity contexts simultaneously.

My plan:

  1. Hook PID resolution functions - Intercept the mechanisms that translate PIDs between namespaces
  2. Create identity confusion - Make processes appear with different PIDs in different namespaces
  3. Cross namespace boundaries - Enable processes to interact across supposedly isolated namespace barriers
  4. Maintain multiple identities - Let processes operate with different identities in different contexts

The Night I Created My First Doppelgänger

I’ll never forget the first time I pulled it off. I had set up multiple containers with strict PID namespace isolation—each container should have been completely unaware of processes in other containers.

I loaded my eBPF program to hook into the PID namespace resolution functions. Then I created a process that appeared to exist in multiple namespaces simultaneously.

It worked. My process had different PIDs in different namespaces, could interact with processes across namespace boundaries, and appeared as a legitimate native process in each environment.

The Perfect Impostor

The beautiful part was that each namespace thought the process belonged to it. The container runtimes saw normal, isolated processes. The monitoring systems showed proper namespace separation. But I had created a process that transcended namespace boundaries.

I had created the perfect impostor—a process that could be anyone, anywhere.

The Techniques I Mastered

Over the following days, I perfected several doppelgänger techniques:

Multi-Namespace Existence: Processes that appear in multiple PID namespaces simultaneously Identity Spoofing: Making processes appear to have different PIDs to different observers Cross-Namespace Communication: Enabling direct process interaction across namespace barriers Namespace Hopping: Moving processes between namespaces without detection Process Masquerading: Making malicious processes appear as legitimate system processes

Each technique exploited the fundamental assumption that PID namespaces provide reliable process isolation.

The Broader Implications

This wasn’t just about confusing process identities—I had discovered that the fundamental assumptions of process isolation could be violated. When you can create process doppelgängers:

  • Break container isolation by enabling cross-container process communication
  • Evade process monitoring by appearing as different processes to different monitoring systems
  • Escalate privileges by masquerading as privileged system processes
  • Establish persistence by creating processes that exist in multiple security contexts

I had broken the basic assumption that processes have single, consistent identities.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to PID namespace functions
  • Implement external process monitoring that doesn’t rely on namespace reporting
  • Use hardware-based process isolation
  • Deploy multiple independent process tracking systems

But I had discovered something fundamental: when you can manipulate process identity at the kernel level, traditional process isolation becomes meaningless.

The Master of Disguise

I had become a master of disguise, capable of creating processes that could be anyone, anywhere. PID namespaces, supposedly providing rock-solid process isolation, had become my playground for identity manipulation.

The doppelgängers were loose, and nobody could tell who was real anymore.

“I had created the perfect impostor—a process that could be anyone, anywhere.”
