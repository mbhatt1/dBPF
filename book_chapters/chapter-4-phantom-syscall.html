Chapter 4: The Phantom Syscall

Bypassing Seccomp Filters with eBPF

February 3rd, 2025 - Questioning Reality Itself

After becoming invisible to audit systems, I thought I had reached the limits of what was possible. But lying in bed last night, I had a disturbing thought that kept me awake:

What if system calls themselves could be phantoms?

I’d been thinking about bypassing security mechanisms, but what if I could make the kernel perform actions that, according to every monitoring system, never happened? What if I could whisper commands directly to the kernel while everyone else thinks I’m sitting quietly?

This morning, I decided to find out.

The Philosophical Breakthrough

This is where my journey got philosophical. I’d been attacking applications, operating systems, even security controls. But what I was about to attempt was an attack on the very concept of observable reality.

I wanted to create phantom syscalls—system calls that execute their intended function but leave no trace in audit logs, process monitors, or syscall tracers.

The uncomfortable truth hit me: modern security is built on the assumption that we can see what processes are doing. Every EDR, every SIEM, every compliance tool relies on being able to monitor system calls.

But what happens when that fundamental assumption breaks down?

Understanding My Target: Seccomp

I spent the morning studying seccomp—the kernel’s bouncer that sits at the syscall entrance and checks IDs. Here’s how it normally works:

  • Syscall filtering based on what you’re trying to do and how you’re trying to do it
  • Three choices for each syscall: allow it, block it, or log it and decide later
  • Container jail that keeps processes from doing anything too interesting

Container runtimes love seccomp because it lets them say “you can only make these 50 syscalls out of the 400+ available.” It’s like giving someone a restricted keychain instead of the master key.

But here’s the thing I realized—seccomp only sees what goes through the normal syscall interface. And I wasn’t planning to go through the normal interface.

My Phantom Strategy

The idea was beautiful in its simplicity. Instead of making forbidden syscalls directly, I would:

  1. Make an allowed syscall that seccomp would happily permit
  2. Hook that syscall with eBPF to intercept it before it does its normal work
  3. Use eBPF helpers to perform the forbidden operations directly in kernel space
  4. Return normal results so the application thinks everything worked normally

The beauty was that seccomp would see the allowed syscall and wave it through. The monitoring systems would log the allowed syscall. But the actual work being done would be completely different.

The Night I Made My First Phantom

I’ll never forget the first time I got it working. I had set up a container with a strict seccomp profile that blocked most file operations. According to the security policy, I shouldn’t be able to read sensitive files.

I made a simple getpid() syscall—completely harmless, always allowed. But my eBPF program intercepted it and used kernel helpers to read a file that should have been forbidden.

The result? The application got the file contents it wanted. The audit logs showed only a harmless getpid() call. The seccomp filter was completely bypassed.

I had created my first phantom syscall.

The Terrifying Implications

The really insidious part was that this didn’t break anything visibly. The syscalls still worked, the kernel still functioned normally, the applications still ran fine. The only thing that changed was that security monitoring suddenly developed blind spots.

I could make processes perform actions without those actions being visible to monitoring systems. It was like having a burglar who’s invisible to security cameras—they can walk right past all your defenses.

My security tools would show a process sitting idle while it was actually escalating privileges, accessing sensitive files, or establishing network connections.

The Phantom Techniques I Developed

Over the following days, I perfected several phantom techniques:

File Access Phantoms: Reading sensitive files through innocent syscalls Network Phantoms: Establishing connections that don’t appear in network monitoring Process Phantoms: Spawning processes that don’t show up in process lists Privilege Phantoms: Escalating privileges without triggering capability monitoring

Each technique used the same principle: make an allowed syscall, intercept it with eBPF, and use kernel helpers to do the real work.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to common syscalls
  • Implement deeper syscall inspection beyond seccomp
  • Use multiple monitoring layers to cross-validate syscall activity
  • Restrict eBPF capabilities more aggressively

But I had discovered something fundamental: when you can execute kernel code directly, traditional syscall monitoring becomes meaningless.

The New Reality I’d Uncovered

This was the moment I realized that with eBPF, I wasn’t just attacking applications or even the operating system—I was attacking the very concept of observable reality.

I had entered a world where actions could happen without being observed, where the fundamental assumptions of security monitoring could be violated at will.

The phantom syscalls were just the beginning.

“I could whisper commands directly to the kernel while everyone else thinks I’m sitting quietly.”
