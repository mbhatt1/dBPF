Chapter 2: The OverlayFS Trojan Horse

Container Escape Through Layer Manipulation

February 1st, 2025 - Breaking Out of the Box

After mastering security control manipulation, the next logical target was container isolation. Containers rely heavily on OverlayFS for filesystem isolation, and here’s the thing—OverlayFS is just more kernel code making decisions about file operations.

If we can influence those decisions, we can break container isolation at the filesystem level.

Understanding the Container Filesystem Stack

Containers aren’t really isolated systems—they’re processes with fancy filesystem tricks:

  • Lower layers: Read-only base image content (Ubuntu, Alpine, etc.)
  • Upper layer: Writable scratch space for container changes
  • Merged view: The unified filesystem that the container sees

The key insight: when you modify a file from the base image, OverlayFS performs a “copy-up” operation from the read-only layer to the writable layer. This copy-up process is where we can strike.

The Attack Vector

We’re going to weaponize the copy-up process itself. Here’s the strategy:

  1. Hook Copy Operations: Attach to functions like ovl_copy_up_one() that handle file copying
  2. Target Selection: Filter for specific files we want to trojanize (system binaries, scripts, etc.)
  3. Permission Modification: Set dangerous permissions (setuid bit) during the copy process
  4. Content Injection: Alter file contents to include backdoors or malicious code

The beauty is that this happens during legitimate filesystem operations, so it looks completely normal.

int hook_overlayfs_copy(struct pt_regs *ctx) {
    // Get the dentry being copied
    struct dentry *dentry = (struct dentry *)PT_REGS_PARM1(ctx);
    
    // Check if this is a target file
    if (is_target_file(dentry)) {
        // Mark for modification during copy
        mark_for_trojanization(dentry);
    }
    
    return 0;
}

SEC("kprobe/ovl_copy_up_data")
int hook_copy_data(struct pt_regs *ctx) {
    // Intercept the actual data copy operation
    // This is where we can modify file contents
    return modify_file_content(ctx);
}

Key Technical Points:

  • Hooks into the actual OverlayFS copy-up mechanism
  • Operates at the VFS layer, below container runtime visibility
  • Modifies files during legitimate filesystem operations

Container Escape Techniques

Setuid Binary Creation: During copy-up, we can set the setuid bit on binaries, creating instant privilege escalation opportunities within the container that can lead to host escape.

Shared Library Injection: Modify shared libraries during copy-up to inject malicious code that gets executed by legitimate processes.

Script Trojanization: Alter shell scripts or other interpreted code during copy-up to include backdoor functionality.

Configuration File Manipulation: Modify configuration files to disable security features or create new attack vectors.

Bypassing Container Security

Runtime Evasion: Container runtimes like Docker and containerd monitor the container’s process space but don’t typically monitor the kernel-level filesystem operations we’re manipulating.

Security Scanner Bypass: Most container security scanners analyze the final filesystem state, not the dynamic copy-up process. Our modifications happen in real-time and can be conditional.

Audit Log Evasion: The modifications appear as normal OverlayFS operations in system logs, making them difficult to distinguish from legitimate activity.

Advanced Techniques

Conditional Trojanization: Only modify files when specific conditions are met (time-based, process-based, etc.) to avoid detection during security scans.

Multi-Stage Attacks: Use the initial container escape to establish persistence on the host system and compromise other containers.

Host Filesystem Access: Once we’ve escaped the container, we can access the host filesystem directly, potentially compromising the entire container host.

Detection and Defense

eBPF Monitoring:

  • Monitor for eBPF programs attached to OverlayFS functions
  • Implement BPF LSM policies to restrict eBPF program loading in container environments
  • Use container runtimes that drop CAP_BPF by default

Filesystem Integrity:

  • Implement file integrity monitoring that operates at the kernel level
  • Use read-only container filesystems where possible
  • Monitor for unexpected setuid binaries in container layers

Alternative Storage Drivers:

  • Consider using storage drivers other than OverlayFS for high-security environments
  • Implement additional isolation layers that don’t rely solely on filesystem namespaces

Why This Works

Container isolation relies on the assumption that the kernel will enforce filesystem boundaries correctly. By operating at the kernel level, we’re below where most container security tools monitor, and our modifications look like legitimate OverlayFS operations.

The fundamental issue is that containers provide process isolation, not kernel isolation. When you can run code in the kernel, traditional container boundaries become advisory.

Impact Assessment

This technique demonstrates that container isolation is only as strong as the kernel mechanisms that enforce it. When those mechanisms become programmable through eBPF, container escape becomes a matter of understanding the right kernel functions to hook.

We’re not breaking containers—we’re using the kernel’s own filesystem management code to break out of them.
