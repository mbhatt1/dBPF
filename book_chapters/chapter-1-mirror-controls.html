Chapter 1: The Mirror Controls

Subverting Kernel Security Mechanisms

January 31st, 2025 - The First Breakthrough

Here’s where things get interesting. I was working with a simple eBPF program to monitor capability checks—just basic observability stuff. But then I realized something: if I can see these security decisions being made in real-time, what’s stopping me from changing them?

That’s when it clicked. Linux security controls aren’t immutable laws—they’re just kernel functions making decisions. And if they’re functions, they can be hooked.

The Core Attack Vector

The Linux Security Module (LSM) framework funnels every security decision through specific kernel functions. Here’s what we can target:

Primary Targets:

  • cap_capable() - Capability checking
  • security_file_permission() - File access control
  • security_task_kill() - Process signal control
  • security_bprm_check() - Binary execution control

The Attack Method:

  1. Hook target functions using kprobe or fentry attachment points
  2. Intercept return values before they reach calling code
  3. Flip denial responses to approval responses
  4. Keep audit logs looking normal to avoid detection

int intercept_capability_check(struct pt_regs *ctx) {
    int ret = PT_REGS_RC(ctx);
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    
    // Target specific process
    if (pid == target_pid && ret != 0) {
        // Convert denial to approval
        bpf_override_return(ctx, 0);
    }
    return 0;
}

Key Technical Points:

  • Uses bpf_override_return() helper to modify function return values
  • Requires CONFIG_BPF_KPROBE_OVERRIDE kernel configuration
  • Operates at the kernel function level, below userspace security tools

Breaking Down the Security Subsystems

Capability System Bypass: The capability system uses cap_capable() to check if a process has specific privileges. We intercept this function and override denials for our target processes while maintaining normal enforcement for everything else.

SELinux/AppArmor Bypass: These mandatory access control systems rely on LSM hooks. We can hook the decision functions before policy evaluation, modify access vector cache (AVC) responses, and preserve the audit trail while changing enforcement decisions.

Seccomp Filter Bypass: Seccomp operates at the syscall level, but eBPF programs can attach to syscall entry points before seccomp evaluation. We can use eBPF helpers to perform forbidden operations directly, bypassing seccomp without triggering filter violations.

Staying Under the Radar

The key to operational security is maintaining expected audit behavior:

  1. Selective Logging: Generate fake denial events while allowing operations
  2. Audit Redirection: Route security events to controlled destinations
  3. Log Consistency: Ensure audit trails match expected security policy enforcement

Anti-Forensics Measures:

  • Use temporary eBPF program loading to minimize detection windows
  • Implement program auto-unloading after achieving objectives
  • Leverage legitimate eBPF usage patterns to blend with normal system activity

Why This Works So Well

Most security tools assume kernel security decisions are immutable. They monitor at higher abstraction layers and trust that the kernel will enforce policies correctly. By operating at the kernel function level, we’re below where most monitoring happens.

The beauty is that everything looks normal from the outside—audit logs show denials, monitoring tools report compliance, security dashboards stay green. But we’re actually operating with god-mode privileges.

Defense Strategies

eBPF Restriction:

  • Remove CAP_BPF and CAP_SYS_ADMIN from untrusted contexts
  • Implement BPF LSM policies to control eBPF program loading
  • Monitor eBPF program attachment to security-critical functions

Integrity Verification:

  • Deploy external security monitoring that doesn’t rely on kernel reporting
  • Implement cross-validation between multiple security enforcement points
  • Use hardware-based security features that operate independently of kernel software

The Bigger Picture

This technique demonstrates that kernel-level programmability fundamentally changes the security model. When security enforcement functions become programmable, traditional security boundaries become advisory rather than mandatory.

We’re not breaking security—we’re becoming the security system itself.

“When you can hook the functions that make security decisions, you become the decision maker.”
