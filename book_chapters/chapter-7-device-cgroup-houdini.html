Chapter 7: Device Cgroup Houdini

The Ultimate Container Escape

February 7th, 2025 - The Ultimate Escape Artist

After silencing SELinux yesterday, I felt invincible. But there was still one challenge that had been nagging at me: device access restrictions. Containers are supposed to be completely isolated from the host’s hardware—no direct device access, no way to touch the underlying system.

But what if I told you that device cgroups, the very mechanism that enforces this isolation, could become your escape hatch?

Today I became Houdini. I learned to slip out of the tightest device restrictions while making it look like I never left my container cell.

The Hardware Prison

I spent the morning studying device cgroups—the kernel’s hardware bouncer. They’re supposed to:

  • Control device access by maintaining allow/deny lists for every device
  • Enforce container isolation by preventing containers from touching host hardware
  • Protect the host from malicious containers trying to access sensitive devices
  • Maintain security boundaries between different container workloads

It’s like having a prison guard who controls which tools each prisoner can access. Containers get a very limited set of “safe” devices, while the dangerous stuff stays locked away.

But what if I could convince the guard that I’m actually a trustworthy maintenance worker who needs access to everything?

My Houdini Strategy

The idea was beautiful in its audacity. Instead of trying to break the device restrictions, I would make the device cgroup system think I was authorized to access whatever I wanted.

My plan:

  1. Hook device permission checks - Intercept the functions that decide whether a process can access a device
  2. Forge authorization - Make my container processes appear to have legitimate device access rights
  3. Maintain the illusion - Keep device restrictions working normally for other containers
  4. Access host hardware - Use my newfound device access to escape container isolation completely

The Night I Became Houdini

I’ll never forget the first time I pulled off the escape. I had set up a container with strict device restrictions—no access to anything except the bare minimum needed to run.

I loaded my eBPF program to hook into the device cgroup permission checks. Then I tried to access /dev/mem—direct access to physical memory, something that should have been absolutely forbidden.

It worked. I was reading physical memory from inside a container. I had escaped the device restrictions without triggering any alarms.

The Perfect Escape

The beautiful part was that the container runtime still thought I was safely locked up. The device cgroup accounting showed normal, restricted access. The security monitoring showed proper isolation. But I was actually accessing host hardware directly.

I had become the ultimate escape artist—breaking out of device restrictions while making it look like I never left my cell.

The Techniques I Mastered

Over the following days, I perfected several device escape techniques:

Memory Access: Direct access to physical memory through /dev/mem Disk Bypass: Raw disk access bypassing filesystem isolation Network Hardware: Direct access to network interfaces GPU Hijacking: Accessing graphics hardware for cryptocurrency mining USB Manipulation: Controlling USB devices from within containers

Each technique used the same principle: make the device cgroup system think I was authorized while maintaining the appearance of proper isolation.

The Broader Implications

This wasn’t just about accessing devices—I had discovered a fundamental flaw in container isolation. When you can bypass device restrictions, you can:

  • Access host filesystems directly through raw disk access
  • Read host memory containing sensitive data from other containers
  • Control host hardware for denial of service attacks
  • Establish persistence by modifying firmware or hardware configurations

I had broken the fundamental assumption that containers provide hardware isolation.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to device cgroup functions
  • Implement hardware-level access controls that don’t rely on software
  • Use external device monitoring that tracks actual hardware access
  • Deploy multiple independent device restriction systems

But I had discovered something profound: when you can forge device authorization, traditional container isolation becomes meaningless.

The Ultimate Escape

I had become Houdini—the ultimate escape artist who could slip out of any device restriction while making it look like I never left my container cell.

The hardware prison had been opened, and the guards didn’t even know the door was unlocked.

“I had become the ultimate escape artist—breaking out of device restrictions while making it look like I never left my cell.”
