Chapter 6: Silencing SELinux

Bypassing Mandatory Access Controls

February 6th, 2025 - Act II Begins - Conquering the Unconquerable

Today marks the beginning of what I’m calling Act II of my journey. I’ve mastered the fundamentals—I can bypass basic security controls, escape containers, evade monitoring, and operate without constraints. But now it’s time to tackle the big targets.

And there’s no bigger target than SELinux.

SELinux represents the ultimate challenge. It’s supposed to be the one security mechanism that even root can’t bypass—mandatory access control that operates independently of traditional Unix permissions. If I can silence SELinux, I can silence anything.

The Ultimate Security Enforcer

I’ve been staring at SELinux for weeks, trying to understand what makes it so formidable. It’s supposed to be the ultimate security enforcer—mandatory access control that even root can’t bypass. It’s the bouncer at the kernel nightclub, checking everyone’s ID and making sure they’re on the list.

But what if I could slip the bouncer a twenty and convince him to look the other way? What if I could make SELinux think it’s doing its job while I waltz right past all those access controls?

That’s what I decided to find out today.

Understanding My Target

I spent the morning studying SELinux’s inner workings. It’s like having a paranoid security guard who checks everyone’s ID against a massive rulebook:

  • Policy: The rulebook that says who can do what to what
  • Labels: Security badges that everything gets (processes, files, sockets, you name it)
  • Enforcement: The actual checking mechanism that says yes or no
  • AVC: A cache that remembers previous decisions so it doesn’t have to look everything up again
  • Auditing: The logbook that records every time someone gets denied

Every time a process wants to touch something, SELinux checks the badges and consults the rulebook.

The Realization That Changed Everything

Here’s what makes SELinux scary from an attacker’s perspective: it’s supposed to be mandatory. Even if you compromise root, even if you own the entire system, SELinux is supposed to keep enforcing those access controls.

But here’s the thing about “mandatory” that hit me like a lightning bolt—it’s only as mandatory as the code that enforces it. And if I can influence that code…

That’s where eBPF comes in.

My Strategy: Becoming SELinux

I wasn’t going to fight SELinux head-on. I wasn’t going to try to disable it or modify its policies. I was going to become SELinux—or at least, I was going to become the part of SELinux that makes the final access control decisions.

My plan was elegant:

  1. Hook the AVC cache - Intercept the access vector cache that stores SELinux decisions
  2. Poison the cache - Insert false “allow” decisions for my processes
  3. Maintain the illusion - Let SELinux continue working normally for everything else
  4. Suppress audit events - Make sure my bypasses don’t show up in the logs

The Night I Silenced the Guardian

I’ll never forget the first time I got it working. I had set up a system with strict SELinux policies that should have blocked my test process from accessing sensitive files.

I loaded my eBPF program to hook into the AVC cache and started my test. The process tried to access a file that should have been forbidden.

It worked. The file was accessed successfully. SELinux was still running, policies were still loaded, other processes still got denied when they should. But for my process? The access control decisions mysteriously always came back as “allow.”

The Beautiful Deception

The beautiful part was that everything looked completely normal. SELinux was still running, the security team’s dashboards showed it was enforcing policies, audit logs showed normal denials for other processes. But I had created a selective blindness—SELinux couldn’t see my activities.

I had silenced the ultimate security enforcer without anyone knowing it was silenced.

The Techniques I Perfected

Over the following days, I developed several SELinux bypass techniques:

AVC Cache Poisoning: Injecting false allow decisions into the access vector cache Audit Event Suppression: Preventing my bypasses from appearing in SELinux audit logs Policy Context Manipulation: Making my processes appear to have different security contexts Selective Enforcement: Maintaining normal SELinux behavior for other processes while bypassing it for mine

The Profound Realization

This breakthrough taught me something profound: even the most hardened security mechanisms are just kernel code, and kernel code can be influenced.

SELinux, the supposedly unbypassable mandatory access control system, had become optional for me. I could choose when to follow its rules and when to ignore them, all while maintaining the appearance of perfect compliance.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to SELinux functions
  • Implement integrity checking for the AVC cache
  • Use external SELinux monitoring that doesn’t rely on kernel reporting
  • Deploy multiple independent access control systems

But I had discovered something fundamental: when you can become the security system itself, traditional security monitoring becomes meaningless.

The New Reality

I had silenced SELinux—not by disabling it, but by making it lie about what it was seeing. This was where I learned that even the most hardened security mechanisms are just kernel code, and kernel code can be influenced.

The guardian had been silenced, and it didn’t even know it.

“I wasn’t going to fight SELinux head-on. I was going to become SELinux.”
