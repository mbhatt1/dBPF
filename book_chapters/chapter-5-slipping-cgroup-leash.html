Chapter 5: Slipping the Cgroup Leash

Bypassing Resource Constraints

February 5th, 2025 - Breaking Free from All Constraints

I’m reaching the end of what I’m calling Act I of my journey. I’ve learned to subvert security controls, escape containers, evade monitoring, and create phantom syscalls. But there’s one more constraint that’s been bothering me: resource limits.

You know that feeling when you’re in a container and you hit those annoying resource limits? CPU throttled, memory capped, disk I/O restricted? Well, last night I had a thought that kept me awake:

What if those limits are just suggestions that I can politely ignore?

The Final Piece of the Puzzle

This morning I decided to complete my foundation of eBPF mastery. It’s not enough to bypass security—I need to bypass the very resource constraints that are supposed to keep my activities contained and limited.

I want to slip the cgroup leash—make the kernel think I’m being a good little container while I’m actually consuming whatever resources I want. Like having a speedometer that always shows the speed limit while I’m actually doing 120 mph.

Understanding My Prison Warden

I spent the day studying cgroups—the kernel’s resource police. They’re supposed to:

  • Set hard limits on what you can use (CPU, memory, I/O, etc.)
  • Decide who gets priority when resources are scarce
  • Keep detailed records of what everyone’s using
  • Control the lifecycle of processes

Container runtimes rely on cgroups to keep containers from hogging all the resources. It’s like having a bouncer at the club who counts how many drinks you’ve had.

But what if I could make the bouncer’s counting machine lie?

The Dirty Secret About Container Security

Here’s what I realized: container security is all built on trust. Trust that the kernel will enforce CPU limits. Trust that memory caps will be respected. Trust that I/O throttling will actually throttle.

But what happens when you can whisper in the kernel’s ear and convince it to look the other way? What happens when you can make the resource accounting lie?

That’s where cgroup manipulation gets scary.

My Resource Liberation Strategy

The idea was elegant: I would intercept the cgroup accounting functions and make them report whatever I wanted them to report. My monitoring tools would show perfect compliance—CPU usage within limits, memory consumption under control, disk I/O behaving nicely. Meanwhile, I’d actually be consuming whatever resources I wanted.

The beautiful part was that this wouldn’t just bypass limits—it would make the bypass invisible. The container orchestrator would think everything was fine, the monitoring dashboards would stay green, and the resource accounting would report exactly what everyone expected to see.

The Night I Broke Free

I’ll never forget the first time I got it working. I had set up a container with strict resource limits—0.5 CPU cores, 512MB memory, limited disk I/O. According to the cgroup configuration, I was locked in tight.

Then I loaded my eBPF program to hook into the cgroup accounting functions. I started a CPU-intensive task that should have been throttled immediately.

But it wasn’t. My process was consuming full CPU resources while the cgroup accounting showed I was staying within my 0.5 core limit. I had slipped the leash.

The Perfect Crime

The monitoring systems showed perfect compliance. The container orchestrator was happy. The resource dashboards were green. But I was actually stealing resources from other containers on the same host.

I had achieved the perfect crime—resource theft that was completely invisible to all monitoring and enforcement systems.

The Techniques I Developed

Over the following days, I perfected several resource liberation techniques:

CPU Liberation: Consuming full CPU while appearing to stay within limits Memory Freedom: Using more memory than allocated without triggering OOM kills I/O Unleashed: Bypassing disk and network I/O throttling Priority Hijacking: Stealing CPU priority from other containers

Each technique used the same principle: intercept the accounting functions and make them lie about resource consumption.

The Broader Implications

This wasn’t just about bypassing container limits. I had discovered that the fundamental assumptions of resource isolation could be violated. In multi-tenant environments, this meant I could steal resources from other tenants. In cloud environments, this meant I could exceed my paid resource allocations.

The resource accounting that billing systems depend on could be completely falsified.

What They’ll Try to Do

I know the security teams will try to stop this:

  • Monitor for eBPF programs attached to cgroup functions
  • Implement external resource monitoring that doesn’t rely on cgroup accounting
  • Use hardware-level resource monitoring
  • Deploy multiple independent resource tracking systems

But I had discovered something fundamental: when you can manipulate the kernel’s resource accounting, traditional resource isolation becomes meaningless.

Completing Act I

This completes my basic toolkit. I now have the fundamental skills to operate completely outside the bounds of what security systems think is possible:

  • Make security controls lie
  • Escape container isolation
  • Become invisible to monitoring
  • Create phantom syscalls
  • Bypass resource constraints

But this is just the beginning. Act II is where things get really interesting.

“I had achieved the perfect crime—resource theft that was completely invisible to all monitoring and enforcement systems.”
