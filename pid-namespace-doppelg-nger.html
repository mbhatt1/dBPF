PID Namespace Doppelgänger: Cross-Namespace Process Manipulation

Wut

A technique that uses eBPF to create process doppelgängers across PID namespaces, allowing attackers to manipulate, monitor, and control processes in isolated containers from the host or other containers. This undermines the fundamental isolation provided by PID namespaces in containerized environments.

Why

Because eBPF + misconfiguration => broken isolation. PID namespaces are a fundamental isolation mechanism in containerized environments, preventing processes in one container from seeing or interacting with processes in other containers or the host. By creating doppelgängers that can reach across namespace boundaries, attackers can monitor, manipulate, or control processes that should be isolated, potentially leading to container escapes or data theft.

Conclusion

eBPF is all you need. The ability to create doppelgängers that can reach across PID namespace boundaries undermines a fundamental isolation mechanism in containerized environments. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls, especially in multi-tenant environments where process isolation is critical.

Technical Details

PID Namespace Architecture

PID namespaces provide:

  • Isolation of process ID space between containers
  • Prevention of cross-container process visibility and manipulation
  • Hierarchical relationship between parent and child namespaces
  • Foundation for container isolation in Docker, Kubernetes, and other platforms

In containerized environments, each container typically has its own PID namespace, with PID 1 being the container’s init process, regardless of its PID in the host namespace.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement namespace transitions and process management. By intercepting these calls, an attacker can:

  1. Hook namespace transitions: Attach to functions like switch_task_namespaces() or copy_process()
  2. Build cross-namespace mappings: Create a table that maps PIDs across namespace boundaries
  3. Monitor isolated processes: Track process activity in containers from the host
  4. Manipulate across boundaries: Send signals or otherwise interfere with processes in other namespaces
  5. Maintain stealth: Preserve the appearance of proper namespace isolation

// Simplified eBPF program to create PID namespace doppelgängers
SEC("kprobe/switch_task_namespaces")
int BPF_KPROBE(hook_switch_ns, struct task_struct *task,
               struct nsproxy *new_nsproxy)
{
    // Get process information
    u32 host_pid = bpf_get_current_pid_tgid() >> 32;
    u32 host_tgid = bpf_get_current_pid_tgid() & 0xFFFFFFFF;
    
    // Get namespace information
    struct pid_namespace *old_ns, *new_ns;
    bpf_probe_read(&old_ns, sizeof(old_ns), &task->nsproxy->pid_ns_for_children);
    bpf_probe_read(&new_ns, sizeof(new_ns), &new_nsproxy->pid_ns_for_children);
    
    // Create a mapping entry
    struct ns_mapping mapping = {0};
    mapping.host_pid = host_pid;
    mapping.host_tgid = host_tgid;
    mapping.old_ns_id = get_ns_id(old_ns);
    mapping.new_ns_id = get_ns_id(new_ns);
    
    // Store the mapping
    u32 key = 0;
    bpf_map_update_elem(&ns_mappings, &key, &mapping, BPF_ANY);
    
    return 0;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to namespace-related functions
  • Unusual patterns of process signals or terminations across namespace boundaries
  • Processes in one container affecting processes in another container
  • Discrepancies between container runtime process listings and actual processes
  • Unexpected access to process information across namespace boundaries

This technique demonstrates why proper eBPF restrictions are critical for maintaining process isolation boundaries, especially in multi-tenant environments where PID namespace isolation is a key security mechanism.

Real-world Impact

In containerized environments, this technique could allow an attacker to:

  • Monitor sensitive processes in other containers
  • Terminate or manipulate processes across container boundaries
  • Inject code or signals into processes in isolated containers
  • Bypass container runtime security controls
  • Perform container escape by manipulating privileged processes

The ability to reach across PID namespace boundaries undermines a fundamental isolation mechanism in container security models, potentially allowing cross-container attacks or container escapes.
