The Mirror Controls: Subverting Kernel Security Mechanisms

Wut

How eBPF turns capabilities, seccomp, SELinux, and other kernel‑enforced controls into mere reflections—fooling auditors while attacks succeed. This technique creates a deceptive mirror where security controls appear to be functioning normally while being completely bypassed.

graph TD
    A[Security Control] -->|1. Enforcement Check| B[Kernel Function]
    C[eBPF Program] -->|2. Hook & Intercept| B
    B -->|3. Modified Decision| D[Allow Operation]
    E[Audit Log] -->|4. False Record| F[Clean Logs]
    G[Security Monitor] -->|5. Sees Compliance| H[False Security]

Why

Because eBPF + misconfiguration => broken isolation. Modern Linux security relies on multiple layers of kernel-enforced controls like capabilities, seccomp, AppArmor, and SELinux. When eBPF can intercept and modify the enforcement points for these controls, the entire security model is compromised while appearing intact—creating a dangerous false sense of security.

Attacker hat on

  1. Identify a target system with eBPF capabilities and security controls
  2. Map the kernel functions responsible for security enforcement
  3. Develop eBPF programs that hook into these enforcement points
  4. Load the malicious BPF programs with appropriate privileges
  5. Modify security decisions to allow otherwise prohibited operations
  6. Ensure audit logs show the expected “denied” messages while operations succeed
  7. Maintain persistence through the eBPF programs

Defender hat on

  1. Remove CAP_BPF from untrusted processes and containers
  2. Implement BPF LSM policies to restrict eBPF program loading
  3. Monitor for unexpected eBPF programs attached to security functions
  4. Use multiple, independent security monitoring mechanisms
  5. Implement integrity verification for security subsystems
  6. Consider using eBPF-based security tools that can detect malicious eBPF usage

Conclusion

eBPF is all you need. The ability to intercept and modify kernel security decisions through eBPF creates a particularly dangerous scenario where attacks succeed while all monitoring systems report compliance. This technique highlights why eBPF capabilities should be treated as highly privileged operations that require strict access controls.

Technical Details

Security Control Architecture

Linux kernel security relies on multiple enforcement mechanisms:

  • Capabilities: Fine-grained privileges that replace the all-or-nothing root model
  • Seccomp: System call filtering to restrict process actions
  • SELinux/AppArmor: Mandatory access controls for resources
  • Namespaces: Resource isolation between processes
  • Cgroups: Resource limiting and accounting

Each of these mechanisms has specific kernel functions responsible for enforcement decisions.

Exploitation Technique

The exploit leverages eBPF’s ability to attach to kernel functions that implement security checks. By intercepting these calls, an attacker can:

  1. Hook enforcement points: Attach to functions like cap_capable(), security_file_permission(), or seccomp_check_filter()
  2. Modify decisions: Change the return values of security checks from “deny” to “allow”
  3. Maintain appearances: Ensure audit logs show the expected “denied” messages
  4. Create false trails: Generate deceptive audit records that mask the actual operations

Detection Methods

Defenders should monitor for:

  • Unexpected eBPF programs attached to security-related functions
  • Discrepancies between security policy and actual system behavior
  • Unusual patterns of eBPF program loading
  • Inconsistencies between different security monitoring systems
  • Processes that appear to function despite security restrictions

This technique demonstrates why proper eBPF restrictions are critical for maintaining the integrity of security controls, especially in environments where multiple layers of security are expected to provide defense-in-depth.
